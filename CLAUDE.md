# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Szikora Transz flottakezelő (fleet management) system: a React admin/driver UI on top of a plain PHP (no framework) REST-ish API, backed by MySQL/MariaDB via PDO. Built on the Notus React (Creative Tim) Tailwind admin template — most of `src/components`, `src/assets`, `src/layouts` are template scaffolding, not app-specific code.

Domain modules (mirrored across frontend views, backend interfaces, and API actions): kamion (trucks), potkocsi (trailers), furgon (vans — self-propelled, full parity with kamion; see "Furgon (van)" below), soforok (drivers), karbantartasok (maintenance records), bejelentesek (incident reports — list/create/edit/delete backend is real, but the in-report message thread is still frontend-only fake data, see "Database schema" below), files, email, esemenyek/egyediHataridok (calendar events / custom deadlines — computed on the fly, no dedicated table).

## Commands

Frontend (run from repo root):
- `npm start` — CRA dev server (localhost:3000)
- `npm run build` — production build into `build/` (also strips template license comments via `gulp licenses`)
- `npm test` — CRA/Jest test runner (no test files currently exist in the repo)
- `npm run build:tailwind` (or `npx tailwindcss -i ./src/assets/styles/index.css -o ./src/assets/styles/tailwind.css`) — rebuild `src/assets/styles/tailwind.css` from `src/assets/styles/index.css`. **This is NOT automatic.** `src/index.js` imports the pre-built `tailwind.css` directly (not `index.css`), so CRA does not recompile Tailwind on the fly. Any new utility class used in JSX must be followed by this rebuild, or it silently won't exist in the stylesheet (e.g. an element with `hidden md:flex` can end up permanently hidden if `.md\:flex` was never compiled in).

Backend (PHP, no build step, no composer dependencies):
- `cd backend && php8.2 -S localhost:8000` — run the API locally (see discrepancy note below)

There is no linter config beyond CRA's default `eslintConfig: { "extends": "react-app" }`, and no PHP test suite.

## Architecture

### Frontend routing
`src/index.js` mounts three independent layouts under `react-router-dom` v5: `layouts/Admin.js`, `layouts/User.js`, `layouts/Auth.js`, plus standalone `views/Landing.js` and `views/Profile.js`. Each layout owns its own `<Switch>` of pages from `src/views/{admin,user,auth}/`. There's no route guard component — auth/role gating happens ad hoc inside pages (check `localStorage`/props usage in view files, not a shared context).

**The real login URL is `/auth/login`** (rendered by `layouts/Auth.js`, which redirects bare `/auth` to it). `layouts/Admin.js` also declares a `<Route path="/login" exact component={LoginPage} />` inside its own `<Switch>`, but that's dead code — `Admin` only ever mounts for paths starting with `/admin` (see the top-level `<Route path="/admin" component={Admin} />` in `src/index.js`), so a bare `/login` URL never reaches it and instead falls through to the catch-all `<Redirect from="*" to="/" />` (Landing page). Don't be misled by it when tracing the login flow, and don't "fix" it into a real redirect without checking whether that's actually wanted — it's unreachable, not broken.

`views/auth/Login.js` branches its entire render on `useMediaQuery({ maxWidth: 1023 })` (the same cutoff as the original design's `lg:` branding-column breakpoint): under 1024px it's a full-bleed dark single-card view; at `lg`+ it's the original two-column light layout with the branding copy. These are two genuinely different JSX trees (not one tree reshaped by Tailwind breakpoints) because the page background color, card background/blur, and whether the branding column exists at all all differ structurally, not just by size — don't try to collapse them back into a shared responsive tree.

**Stacking-context gotcha in `layouts/Auth.js`**: `AuthNavbar` (the floating "Főoldal" pill top-left) is `position: absolute; z-index: 50`, a sibling of the routed `<Switch>` content. That `<Switch>` used to be wrapped in `<div className="relative z-10">` — the `z-10` on that wrapper (not `relative` alone — `relative` without an explicit `z-index` doesn't do this) creates its own stacking context, which means everything inside it, including `Login.js`'s own `fixed inset-0 z-[9999]` full-screen overlay, gets flattened to a single z-10 layer from the *outside* stacking context's point of view. Since 10 < 50, `AuthNavbar` always painted on top of Login's supposedly-opaque overlay, no matter how high Login's own z-index was set — a real bug that predates this session's changes but only became visible once Login became a true full-bleed overlay. Fixed by dropping the `z-10` (kept `relative`, which is still needed to stack this div above the section's own absolutely-positioned background/grain-overlay divs via plain DOM order — no `z-index` required for that). If a future full-screen overlay component (another modal-like page, a lightbox, etc.) seems to render *behind* something with a much lower z-index, check every ancestor for an unnecessary `z-*` class creating an intermediate stacking context — the fix is almost always to remove that ancestor's z-index, not to raise the overlay's.

### API communication
All API calls funnel through two helpers in `src/utils/`:
- `fetchAction(action, payload)` — POSTs `{ authHash, action, ...payload }` as JSON to `api.php` and returns the parsed JSON response `{ success, ... }`.
- `downloadFileAction(id, filename)` — same pattern, but decodes a base64 file from the response and triggers a browser download.

The API base URL and `authHash` are hardcoded client-side constants in each of these files (dev: `http://localhost:8001/api.php`, prod: `https://szikora-transz.hu/backend/api.php`). **Note the dev port mismatch**: `todo.txt` documents running the PHP server on port 8000, but the frontend code points at port 8001 — start PHP accordingly (`php8.2 -S localhost:8001`) or update both `src/utils/*.js` files if changing this.

### Backend API dispatch
Single entrypoint `backend/api.php` decodes the JSON POST body and delegates everything to `ApiHandler` (`backend/ApiHandler.php`). `ApiHandler`:
- Declares every valid action + its required parameters in `getActions()` (a flat action-name → required-fields map).
- `validation()` checks the shared `authHash` (from `backend/config.php`), that the action exists, that required params are present, and does ad hoc email validations.
- `process()` is a large `switch` over `$action` that dispatches to methods on `ApiHandler` itself or to the per-domain interface classes required at the top of the file (`backend/interface/*Interface.php` — one per domain module listed above).

To add a new API action: add it to `getActions()` with its required params, add a `case` in `process()`, and implement the logic either inline in `ApiHandler` or in the relevant `interface/*Interface.php` file.

**To add a brand-new `interface/*Interface.php` file** (a new domain module, not just a new action on an existing one), three edits are required in `ApiHandler.php`, not two — it's easy to do the first two and get a fatal error anyway:
1. `require 'interface/xInterface.php';` near the top with the others.
2. Instantiate it (same pattern as the existing `$xInterface = new XInterface($this->db);` block).
3. **Add the new variable name to the single `global $kamionInterface, $potkocsiInterface, ...;` statement inside `process()`** (around line 532). This is the one that's easy to forget — `require` + instantiation alone are not enough, because `process()` only sees interface objects that are explicitly named in that one `global` list. Forgetting step 3 fails as "Call to a member function X() on null", not as a missing-require error, which makes it a confusing failure mode if you don't know to check this list.

`backend/db.php` defines `Database::connect()` (PDO/MySQL, DB name `kamion`) with credentials hardcoded in the class — same pattern in `backend/config.php` for the shared `authHash`. There is no `.env`/secrets layer; secrets live directly in these two PHP files.

### Session & permission model
Every admin-facing action that mutates or reads scoped data resolves identity **server-side from the `sessions` table**, never from client-submitted `kerelmezo_id`/`admin`/`ceg_id` fields (those are accepted for backward-compatible request shape and cross-checked against the resolved session, but never trusted as the source of truth — this was the subject of a full security-audit pass; see git history around `Implement security enhancements and validation checks across various interfaces`). Key helpers in `ApiHandler.php`:
- `resolveKerelmezo($request)` — resolves the caller's `admin` table row from `sessions`, requires an admin-type session (throws otherwise), and computes `is_root`/`ceg_id`. Throws if a client-submitted `ceg_id` doesn't match.
- `resolveSajatSoforId($request)` — the sofőr-session equivalent; requires a `sofor`-type session, returns that sofőr's own id. Used for driver self-service actions (jármű-váltási kérés, etc.) so a driver can't act on another driver's behalf.
- `resolveSajatCegId($request)` — works for **either** session type (admin or sofőr), always returns the real owning company id server-side. Used by actions reachable from both roles (file upload, etc.).
- `requireAdminRole($request)` / `hivoSajatSzerepkoreAdmin($request)` (throwing vs. non-throwing; the non-throwing one was renamed from `kerelmezoAdmin` on 2026-07-19 — the old name read as if it did row-ownership checking, it doesn't) — checks `is_root || szerepkor === 'admin'`, for admin-only fields/actions (e.g. bér visible only to admin, not to a fuvarszervező role viewing the same sofőr record). It does **not** check that a target row belongs to the caller — see the audit note below for why that distinction mattered.
- `requirePermission($request, $modul, $tipus)` — checks the configurable per-role module permission (`Jogosultsagok` admin page) via `MODULE_PERMISSION_MAP` (action → `[modul, tipus]`); `ADMIN_ONLY_ACTIONS` is a flat list of actions that bypass the configurable map entirely and are always admin/root-only (team/role/permission management itself).

**Team members share the `admin` table, not a separate table**: `admin.tulajdonos_admin_id` is `NULL` for the root/owner account and points at the owner's `admin.id` for every csapattag (team member) invited under that company. `ceg_id` (the actual tenant-scoping key used everywhere data is filtered) is **not** the logged-in user's own `admin.id` — it's `is_root ? id : tulajdonos_admin_id`. Any new query/action that scopes by "the current admin's data" must use this resolved `ceg_id`, not the bare session `felhasznalo_id`, or a team member's actions will silently operate on/leak the wrong slice of data (this exact bug class — trusting client-submitted `admin`/`ceg_id` instead of resolving it — was the root cause of the account-takeover and cross-tenant findings fixed in the security audit).

**Client-side auth persistence: `localStorage`, not `sessionStorage` (changed 2026-07-18)**. The `user`/`sessionToken` pair that every `PrivateRoute` (`layouts/Admin.js`, `layouts/User.js`) and `fetchAction`/`downloadFileAction` reads is now written to `localStorage` everywhere (~60 files, all consistent — `sessionStorage` was previously used exclusively for these two keys and nothing else, so this was a safe global rename, not a partial migration). **Why**: `sessionStorage` is scoped to the browsing-context/tab's lifetime, which mobile browsers and standalone-PWA processes (`public/manifest.json`'s `display: "standalone"`) routinely tear down and recreate under memory pressure or after being backgrounded — this silently wiped the "logged in" state even though the backend's own `sessions` row (30-day expiry, `ApiHandler::loginUser()`) was still perfectly valid, forcing a full re-login that looked like a bug but was really just `sessionStorage` doing exactly what it's spec'd to do. `localStorage` persists until an explicit logout (`localStorage.removeItem` calls, now consistent across all logout call sites — `UserDropdown.js` previously forgot to clear `sessionToken`, only `user`, fixed alongside this change) or a real "session expired" response from the backend (`fetchAction.js`'s `handleExpiredSession()`).
- `views/auth/Login.js` now also auto-redirects on mount if `localStorage.getItem("user")` is already present (`is_admin` decides `/admin/dashboard` vs `/user/dashboard`, via `history.replace` so back-navigation can't loop to the login form) — this matters because `manifest.json`'s `start_url` is hardcoded to `/auth/login`, so every fresh PWA launch used to render the login form for a split second (or, pre-fix, force a real re-login) even for an already-authenticated user.
- The backend session itself was **not** changed (still a fixed 30-day expiry from login, no sliding/refresh-on-activity logic, no cleanup cron for stale rows) — the mobile "keeps asking to log in" complaint was fully explained by the client-side storage choice, not the server-side expiry window, so that was left alone rather than widened speculatively.
- Verified locally end-to-end (not just read the code): inserted a real row into the local `sessions` table for `admin.id=1`, drove it through Playwright — direct navigation to `/admin/dashboard` with only `localStorage` populated stays authenticated, `/auth/login` auto-redirects away when already authenticated, and a **brand-new browser context** (`storageState` carrying over only `localStorage`, simulating a killed-and-relaunched mobile app process) still lands on `/admin/dashboard` without hitting the login form — this is the actual scenario that was broken before.

### Security/logic audit and fix pass (2026-07-19)
A full adversarial review (5 independent passes: auth/session/IDOR, SQL/data-integrity, external integrations/file handling, frontend, business logic) found a **systemic cross-tenant IDOR problem**: the resolve-server-side pattern documented above existed and was correctly used in some modules (`ugyfelInterface.php`, `csapatInterface.php`, `koltsegInterface.php`, `jarmuValtasInterface.php`) but **not** in most others — `kamion`/`potkocsi`/`furgon`/`soforok`/`bejelentesek`/`szabadsag`/`helyszin`/`karbantartasok`/`tankolas`/`files` interfaces trusted client-submitted `id`/`ceg_id`/`admin`/`sofor_id` fields directly in their SQL, and several dispatcher-level actions (`getUgyfelek`, `newUgyfel`, `getCsapattagok`, `globalSearch`, `getAuditLog`, `getKarbantartas`/`getPotkocsiKarbantartas`/`getFurgonKarbantartas`, `getSum`, `getEsemenyek`, `getAdminElerhetoseg`, the `EgyediHatarido` family) required `ceg_id`-shaped params under a *different* field name (`id`), which meant `resolveKerelmezo()`'s existing `ceg_id`-match check silently never fired for them even though the helper itself was correct. All of these were fixed by always passing a server-resolved id (`resolveKerelmezo()['ceg_id']` / `resolveSajatCegId()` / `resolveSajatSoforId()`) into the interface layer instead of the raw request field, and adding the missing `WHERE ... AND admin = :ceg_id`/`torolt <> 'I'` scoping inside the interface methods themselves (defense in depth — scoped at both the dispatcher and the query).

Other fixes from the same pass, still in force as conventions:
- **`backend/interface/filesInterface.php::getFiles()`** had a live parameter-count bug (caller passed 6 args, function accepted 5 — PHP silently dropped the `$ceg_id` arg) that made the non-`admin`-tabla branch's `WHERE admin = :ceg_id` bind to `NULL`, so it always returned an empty list for any real `tabla` (kamion/potkocsi/furgon/sofor/karbantartasok file attachments) — this was a live functional regression, not just a security gap, now fixed.
- **`backend/interface/jarmuValtasInterface.php::elbiralJarmuValtas()`** now re-validates the target vehicle still exists (`torolt <> 'I'`) and isn't already assigned to a *different* active driver at approval time (not just at request time), and the approval branch sets the kamion/furgon columns mutually-exclusively (`kamion = X, furgon = NULL` or vice versa) — previously a driver approved for a furgon after already having a kamion assigned would end up with both columns non-null, causing `Tankolas.js` to silently attribute fuel log entries to the wrong vehicle.
- **`backend/ApiHandler.php::getEsemenyek()`** and **`backend/cron/lejarat_emlekezteto.php`** gained a third `furgon` branch (mirroring kamion/potkocsi) — furgon expiry dates and planned maintenance were previously completely invisible to both the admin calendar and the daily reminder email.
- **`backend/cron/*.php`** now guard `if (PHP_SAPI !== 'cli') { http_response_code(403); exit; }` — they live under `backend/` (webroot) with no `.htaccess` exclusion and no auth of their own, so they were directly HTTP-callable by anyone before this.
- **`backend/cron/lejarat_emlekezteto.php`** now de-duplicates via a new `lejarat_emlekezteto_log` table (`admin_id`+`datum` composite PK, `backend/sql/29.sql`) — it previously had no "already sent today" guard and would re-send the full reminder on every run.
- **`requestPasswordReset`** now rate-limits to 3 requests per email per 15 minutes (silently, still always returns `success:true` to avoid account-enumeration) — previously unlimited.
- **`ApiHandler::validation()`** now checks `is_string($request['action'])` before the `array_key_exists()` lookup, and `process()`'s catch broadened from `Exception` to `\Throwable` — a non-string `action` (e.g. a JSON array) previously caused an uncaught `TypeError` (pre-auth, since this runs before session validation), breaking the JSON response contract.
- **`layouts/Admin.js` / `layouts/User.js`** `PrivateRoute` now checks `user.is_admin` in addition to bare login state — previously a logged-in driver session could navigate to `/admin/...` URLs directly (and vice versa), landing on a broken/empty page since the *backend* rejected the underlying calls but the *route* didn't.
- Session expiry comparison in `requireValidSession()` moved from PHP `strtotime()` to a SQL-side `(lejarat < NOW())` — same PHP/MySQL timezone-mismatch class documented elsewhere in this file.
- `koltsegInterface.php`'s `newEgyebKoltseg`/`updateEgyebKoltseg` now reject a tétel with more than one of `kamion_id`/`potkocsi_id`/`furgon_id` set (previously only enforced client-side; double-set would double-count the tétel in the jármű-bontás table).
- `piaciArakInterface.php::getArfolyam()` now validates the currency code against `^[A-Z]{3}$` before it reaches the XPath query in `lekerdezMnbArfolyam()` (was a theoretical XPath-injection point, low impact since the queried document is MNB's own public rate list, not sensitive).
- **Not fixed, needs a deliberate ops decision**: the NAV/GPSmart credential encryption key (`backend/config.php`'s `navEncryptionKey`) lives in the same committed file as the data it protects. Rotating it would invalidate every already-stored encrypted NAV/GPSmart credential (every tenant would need to re-enter them), so this wasn't done silently as part of this pass — flagged for a future coordinated rotation+re-encryption migration instead.
- All fixes were verified against the live local DB (not just read) — a temporary second company/admin/driver/vehicle was created, the original exploits were re-run and confirmed blocked (with the DB state checked before/after), then the test rows were deleted. A real admin session was also driven through the actual browser (`/admin/kamionok`, `/soforok`, `/helyszinek`, `/koltsegek`, `/ugyfelek`, `/dashboard`) to confirm the fixes don't regress legitimate access.

### SQL migration convention
`backend/sql/N.sql` files are numbered, sequential, one-shot-committed migrations (currently up to `27.sql`). **Before creating a new numbered file, check `git status`/`git log` for the most recent one**: if it's still uncommitted, append new schema changes to that SAME file instead of creating `N+1.sql` — only start a new file once the previous one has actually been committed. This is a deliberate, durable convention (explicitly requested), not an oversight — it keeps a single work-in-progress migration file per logical unit of work instead of fragmenting one feature's schema changes across several small numbered files.

### Deployment
`genezio.yaml` configures frontend-only deployment (builds via `npm install && npm run build`, publishes `build/`). The PHP backend is deployed separately (see `build/api_proxy.php` and prod URL `https://szikora-transz.hu/backend/api.php`) and isn't managed by the genezio config.

### Database schema (`kamion` MySQL/MariaDB DB)
Inspected directly via `information_schema` (local DB, see "Local dev environment" below). Key facts not obvious from the PHP code alone:

- **Every table uses the `MyISAM` engine, not InnoDB** — so there are **no real foreign-key constraints** anywhere in the schema, even though several index names look like they should be one (`CarNaplo_carId_fkey` on `kamion_karbantartars.kamion_id`, `Car_rendszam_key` on `kamion.rendszam`, `User_email_key` on `user.email`). Referential integrity (`kamion.admin` → `admin.id`, `kamion_karbantartars.kamion_id` → `kamion.id`, `user.kamion` → `kamion.id`, etc.) is convention-only, enforced by application code, never by the DB. Don't assume a delete/update will cascade or get rejected — it won't, either way.
- Those Prisma-style constraint names (PascalCase model names like `Car`, `CarNaplo`, `User` baked into index names that live on snake_case Hungarian tables like `kamion`, `kamion_karbantartars`) are a strong signal this schema was originally scaffolded via Prisma with English model names, then the actual table names were changed to Hungarian later — the old constraint names never got renamed.
- **Soft delete everywhere**: every table has `torolt ENUM('I','N') NOT NULL DEFAULT 'N'` (`I` = igen/deleted, `N` = nem/not deleted). There's no view or trigger hiding deleted rows — every hand-written query must include `WHERE torolt <> 'I'` (or `= 'N'`) itself, or it'll silently include soft-deleted rows.
- **Per-admin ownership**: `kamion`, `potkocsi`, `furgon`, `kamion_karbantartars`, `potkocsi_karbantartars`, `furgon_karbantartars`, `fajlok`, `egyedi_hataridok` all carry an `admin` column pointing at `admin.id` — each admin account owns its own slice of fleet data; nearly every list/get query in `ApiHandler`/interfaces scopes by `WHERE admin = :id`.
- Table purposes, beyond what's in "Domain modules" above:
  - `admin` — the admin/company-user accounts (not "administrator" in a generic sense — this is *the* login table for admin-role users, parallel to `user`).
  - `user` — actually **sofőrök (drivers)**, despite the generic name; `user.admin` → owning admin, `user.kamion`/`user.furgon` → their currently assigned `kamion.id`/`furgon.id` (mutually exclusive in practice, not enforced by the DB).
  - `kamion.potkocsi` is `NOT NULL` — the schema assumes every truck row references exactly one trailer row at all times (no "no trailer attached" state representable without pointing at some `potkocsi` row). `furgon` has **no** equivalent column — a furgon never tows a semi-trailer.
  - `fajlok` — generic polymorphic attachments table: `tabla` enum (`kamion`/`potkocsi`/`furgon`/`sofor`/`egyeb`/`admin`/`karbantartasok`) + `rowid` (indexed) says which row in which domain table the file belongs to. This is what `getFiles`/`fileUpload`/`deleteFile` actually use.
  - `kamion_fajlok` / `potkocsi_fajlok` — an older, differently-shaped per-domain file table (`session_id`/`client_id`/`fh` columns), currently **0 rows in both** — looks superseded by the generic `fajlok` table above; don't build new file-upload features against these.
  - `egyedi_hataridok` — custom one-off deadlines (`admin`, `leiras`, `datum`).
  - **`bejelentesek` (incident reports) IS a real table with a real CRUD backend** (`backend/interface/bejelentesekInterface.php`: `getBejelentesek`/`newBejelentes`/`saveBejelentesData`/`deleteBejelentes`/`generateKarbantartasFromBejelentes`, all real `SELECT`/`INSERT`/`UPDATE` against the table) — an earlier version of this doc claimed the whole feature was fake/stub scaffolding; that was true once but is no longer accurate for the list/create/edit/delete part. What's still genuinely fake: the `getMessages`/`sendMessage` actions the frontend chat/message-thread UI (`CardBejelentesek.js`) calls **don't exist anywhere in `ApiHandler::getActions()`/`process()`** — only the in-report message THREAD is frontend-only scaffolding with no backing data.
- **The event calendar has no dedicated table.** `ApiHandler::getEsemenyek()` computes the feed on every request by scanning expiry-date columns across `user` (jogsi/szemelyi/gki/adr lejárat), `kamion`/`potkocsi` (műszaki/poroltó/adr/tachográf/emelőhátfal/kötélzet/kaszkó lejárat, plus insurance payment schedules run through `calculateNextPaymentDate()`), then appending `egyedi_hataridok` rows and `kamion_karbantartars`/`potkocsi_karbantartars` maintenance dates — all merged into one flat array. There's nothing to migrate/query directly for "events"; to add a new event source, add another block to `getEsemenyek()`.

### PHP/MySQL timezone mismatch (general gotcha)
MySQL's `NOW()` evaluates in the OS/server timezone (CEST/UTC+2 on this machine); PHP's `date()`/`time()`/`strtotime()` evaluate in whatever `date_default_timezone_get()` returns (UTC on this machine). Any code that fetches a naive `DATETIME` string from MySQL and round-trips it through PHP's `strtotime()`/`time()` to compute an age or delta gets silently corrupted by the timezone skew (hit this building the Piaci árak cache-freshness check — a "refetch if older than 1 hour" comparison was always evaluating false because of a consistent ~2 hour offset). **Fix pattern: compute time deltas in SQL** (`TIMESTAMPDIFF(SECOND, some_datetime_col, NOW())`) instead of pulling the DATETIME into PHP and comparing there — both sides then evaluate against MySQL's own clock consistently.

### External data integrations
- **NAV Online Számla** (`backend/interface/navSzamlaInterface.php`, `backend/NavSzamlaClient.php`) — per-company technical-user credentials stored (encrypted) in `nav_szamla_beallitasok`, keyed by `ceg_id` (company-level, not per-login — see "Session & permission model" above for why team members share a `ceg_id`, not their own `admin.id`). Manual query-and-approve workflow (not automatic daily sync, by deliberate choice): admin queries a date range, reviews a digest list of NAV-reported invoices (OUTBOUND→bevétel, INBOUND→kiadás), and explicitly selects which to import into `egyeb_koltsegek`. Already-imported invoices are de-duplicated by matching `szamlaszam`. Non-HUF invoices **are** imported (see "Deviza" below for how) — NAV always supplies a HUF-equivalent per invoice regardless of billing currency.
- **Piaci árak (market prices)** (`backend/interface/piaciArakInterface.php`) — EUR/HUF and USD/HUF from the MNB (Magyar Nemzeti Bank) free SOAP webservice (`mnb.hu/arfolyamok.asmx`, `GetCurrentExchangeRates()`), and a benzinár (fuel price, ESZ-95) scraped from NAV's official monthly reference-price page. There is **no free, key-less, genuinely real-time Hungarian fuel-price API** — the NAV monthly official reference price was chosen as the most authoritative available free source (it's the figure Hungarian businesses actually use for reimbursement), not a live/per-minute price. Results are cached in a non-tenant-scoped `piaci_arak` table (deliberately **not** `ceg_id`-scoped, unlike almost everything else in this schema — exchange rates/fuel prices are identical for every company, so per-tenant storage would be pure duplication) with per-source TTLs (1h for FX, 12h for fuel price) via `frissitVagyOlvas()`. On a fetch failure the last successfully-cached value is served and `frissitve` is left pointing at the last genuinely successful fetch (never bumped for a failed attempt) — graceful degradation, not an error surfaced to the UI. NAV's page embeds its price table as JSON-artifact text (HTML-entity-escaped, containing literal `\n` escape sequences that are *not* real whitespace) — parsing requires `html_entity_decode()` **and** a separate `str_replace(['\n', "\xc2\xa0"], ...)` pass before `is_numeric()`/`trim()`, or the extracted value silently fails to parse as a number. Rendered in the desktop sidebar only (`src/components/Sidebar/PiaciArakPanel.js`, mounted in `Sidebar.js` between the scrollable nav list and the fixed account footer — see "Mobile navigation" below for why that placement keeps it always-visible and automatically mobile-hidden for free) with a 5-minute client poll (cheap, since it's normally just hitting the DB cache).
  - **Market-intelligence rebuild** (UX-audit driven — see "UX-audit consistency pass" below): a `piaci_arak_elozmeny` table (`kulcs`+`datum` composite PK, one row per key per calendar day, written via `ON DUPLICATE KEY UPDATE` inside `frissitVagyOlvas()` on every genuine cache refresh — never fabricated/backfilled) now backs a real day-over-day `valtozasSzazalek` and a `getElozmeny($kulcs, $napok=7)`-sourced sparkline, replacing what would otherwise be a misleading "trend" computed from just two cache reads. `CIMKEK` gained a `csoport` key (`Árfolyamok`/`Üzemanyag`) the frontend groups by, and `IDOSZAK_CIMKE` supplies the "vs what" caption per key (e.g. "előző munkanaphoz képest" for FX, "előző havi árhoz képest" for fuel — kept short after a longer version got `truncate`-clipped in the sidebar's narrow column). `PiaciArakPanel.js` was rewritten around this: icon badges, a %-delta pill (emerald/red/slate), an inline SVG sparkline (only rendered once `elozmeny.length >= 2`), and a footer that shows the **oldest** `frissitve` among all items with a colored freshness dot — because the history table only starts accumulating from deploy time, a freshly-migrated environment shows no sparklines until a few natural cache-refresh cycles have passed; this is expected, not a bug.
- **GPSmart flottakövető** (`backend/interface/gpsmartInterface.php`) — session-cookie-based HTML scraping (not a real API) via `DOMDocument`. `MAX_UTVONAL_NAPOK = 7` caps route/waybill query ranges to prevent PHP execution-timeout crashes on large date ranges. Also backs `getKihasznaltsagiRiport()` (fleet utilization/idle-time report, reusing the same 7-day cap and the existing `idoSzovegOraDecimalra()` duration-parsing helper). A vehicle's GPSmart-internal `car_id` is **not** `kamion.id` and isn't stored anywhere — it's resolved live on every use by matching rendszám via `lekerdezPoziciok()` against the company's own GPSmart account namespace.
  - **Napi km-gyorsítótár** (`gpsmart_napi_km` table, `GpsmartInterface::frissitNapiKm()`/`getNapiKmHianyzoNapok()`, `backend/cron/gpsmart_km_cache_frissites.php`) backs the Pénzforgalom Ft/km column. Read (`koltsegInterface::kmOsszesito()`) and write are strictly separated: the write side (route-scraping, potentially slow) only ever runs from the cron, never from a page load — `getKoltsegOsszesito()` only does a cheap `SUM`/`COUNT` read against the cache table, so the Pénzforgalom page can never be slowed down or timed out by GPSmart itself. The **cron is deliberately bounded and incremental** (`MAX_CSOMAG_JARMUVENKENT = 2` seven-day chunks per vehicle per run) rather than trying to backfill an entire gap in one pass — for a company that doesn't open the app for weeks, a single unbounded backfill risks a PHP timeout (chaining many `MAX_UTVONAL_NAPOK`-capped GPSmart calls) and, worse, a *partial* one silently mixed into an aggregate would look complete while actually being wrong. **Today's date is never cached** (a truck can still be mid-route), so a day only ever becomes a permanent cache row once it's fully in the past; a missing row and "the date is today" are treated identically as "not yet knowable." Because the cache can legitimately be incomplete for a given range (sparse cron runs, a company that rarely opens the app), `getKoltsegOsszesito()`'s response carries `kmLefedettseg` (% of requested days actually cached) alongside `bevetelPerKm`/`kiadasPerKm`, and the frontend (`PerKmErtek` in `Koltsegek.js`) prefixes the figure with `~` and a tooltip whenever coverage is under 100% — the app never presents a per-km figure computed from a silently-incomplete denominator as if it were exact.
  - **"Megtett út (ma)" on Flottakövetés** — went through two designs; the second replaced the first outright (no `gpsmart_nap_kezdo_km` table anymore, that migration block and its local table were removed). **v1 (odometer-diff, DB-only, no new GPSmart calls)**: locked in each vehicle's first-seen-today `km` (odometer) reading as a baseline, computed the delta live. Abandoned because live-verified against a real GPSmart account, the `km` field came back **empty for most vehicles** (no CAN-bus/odometer integration on those GPS units) — the feature would show "—" almost everywhere in practice. **v2 (current)**: `GpsmartInterface::lekerdezMegtettUtMa($ceg_id)` reuses the same GPS-based route-query mechanism `ElozmenyekModal.js` already uses for one vehicle at a time (`lekerdezUtvonal($carId, today, today)` → `osszesito.tavolsag_osszesen`), just run across every GPSmart-paired vehicle in the fleet. This is reliable (works off GPS movement, not a vehicle sensor) but **meaningfully slower** — each vehicle is its own fresh login + HTML-scrape (`GpsmartClient` never caches a session cookie). Because of that cost, it's wired up as its own action (`gpsmartMegtettUtMa`, own `getActions()`/`MODULE_PERMISSION_MAP`/`process()` entries) that the frontend calls **only** on initial page load and on the manual "Frissítés" click (`Flottakovetes.js`'s `loadMegtettUt()`/`handleFrissites()`) — never on the automatic 60s position-poll interval, so a slow fleet-wide route-query can never stall the fast, frequently-refreshing map/list. The two calls fire concurrently and independently on "Frissítés" (neither `await`s the other; live-measured: positions done in ~0.5s, distance in ~2s for a small fleet) — merged into the position array client-side in `Flottakovetes.js`'s `dusitett` `useMemo` by `kamion_id`, not returned embedded in `gpsmartPoziciok`'s response. Per-vehicle failures are caught and yield `megtettUtMa: null` for that vehicle only (same defensive pattern as `getKihasznaltsagiRiport()`), never a fabricated `0`. `FlottaKpiKartyak.js`'s tile and `JarmuLista.js`'s "Km ma"/`JarmuReszletek.js`'s field all show the real fetch-freshness (`toLocaleTimeString`) rather than a "since HH:MM" baseline framing, since v2 has no baseline concept.
  - **Gotcha — fuel-level display was removed from Flottakövetés entirely** (KPI tile, `JarmuReszletek.js`'s "Üzemanyag" field, and the low-fuel gas-pump icon on `JarmuLista.js` rows) — explicit user request, not a bug fix. `gpsmartHelpers.js`'s `uzemanyagSzazalek()`/`vanMegbizhatoUzemanyagAdat()`/`alacsonyUzemanyag()` and the `_uzemanyagSzam`/`_alacsonyUzemanyag` fields on `dusitottPoziciok()`'s output were deleted along with it — nothing else in the codebase referenced them (verified via grep before deleting; `Koltsegek.js`'s `uzemanyag` fields are the unrelated Pénzforgalom fuel-*expense* category, not GPSmart fuel-level telemetry). If a fuel-level feature is ever requested again, note it'll hit the same reliability problem odometer did: the raw `uzemanyag` field also reads `0%` unreliably for sensor-less GPS units (this was already handled defensively before removal — 0% was treated as "no sensor," not "empty tank" — but the display itself is gone now regardless).
  - **Gotcha — `JarmuReszletek.js`'s action-button row was invisible without scrolling**: the panel (`xl:h-[640px]`, fixed) had accumulated enough field rows (driver, 4-field grid, address, position coordinates, heading, last-update) that the button grid at the bottom was pushed below the panel's own scroll view — live-verified via screenshot, the buttons genuinely didn't render on screen at all, not just a low-visibility issue. Fixed two ways together: (1) removed the "Pozíció" (raw lat/lon) and "Irány" (heading) fields entirely — low information value, freed real vertical space (the underlying `jarmu.lat`/`lon`/`irany` data is untouched, still used by the Navigálás link and the map pin rotation, only their standalone display rows are gone); (2) "Előzmények" — flagged as the most frequently used action — now renders as its own full-width, brand-filled (not outline) button directly under the field list, with Navigálás/Követés demoted to a plain row below it (originally a 3-column row that also included a "Vezetési idő" button; that whole feature — and the button — was removed later, see below), rather than all being visually equal in one grid. If more fields are ever added back to this panel, re-check that the button row still renders without scrolling before shipping — this class of bug (content silently pushed out of a fixed-height panel) won't throw an error, it just quietly disappears.
  - **Removed: "Vezetési idő" (driving/rest-time logging) feature** (2026-07-17) — the whole EU 561/2006 compliance-log feature (driver-facing `src/views/user/VezetesiIdo.js`, admin `src/views/admin/VezetesiIdo.js`, `backend/interface/vezetesiIdoInterface.php`, the `backend/cron/vezetesi_ido_javaslat_frissites.php` cron, and all nav entries in `Sidebar.js`/`User.js`/`Admin.js`/`Dashboard.js`) was deleted at the user's explicit request — no product-decision context beyond that, unlike the Fuvarok removal above. **Left in place, on purpose**: the `vezetesi_naplo` and `gpsmart_vezetesi_javaslat` DB tables (no destructive migration, same convention as the Fuvarok removal), and `Naplo.js`'s `TABLA_LABEL.vezetesi_naplo` entry (so old audit-log rows still render a friendly label). `GpsmartInterface::lekerdezMegtettUtMa()` — which also powers the unrelated "Megtett út (ma)" Flottakövetés feature above — was only surgically trimmed (removed the side-effect block that used to piggyback on its GPS call to update the now-deleted cache), not deleted; its `getSoforIdKamionSzerint()`/`frissitVezetesiJavaslatCache()` helper methods, which existed only for that side effect, were removed along with it. If this cron was ever registered in the actual server crontab (outside this repo — not discoverable from source alone), it needs to be unregistered there too.
  - **Gotcha — `JarmuLista.js`'s desktop table panel is narrow (~300–320px at the old `xl:col-span-3` of 12)**: adding the "Km ma" column as a 5th column with `table-fixed` + percentage widths visibly truncated the rendszám to 1 character (live-verified). Fixed by dropping `table-fixed` entirely (columns auto-size to content via `min-w` hints on each `<th>` instead of forced percentages) and widening the list panel to `xl:col-span-4` (map dropped to `xl:col-span-5` to compensate) in `Flottakovetes.js`. The list's `overflow-auto` wrapper is a deliberate safety net, not decoration — even after the above, the table's natural content width (StatusBadge's own padding around a 9-character "Mozgásban" pill turned out to be the single biggest column, wider than its `min-w` guess) slightly exceeds the panel at this vehicle count, so the least-critical column (relative last-seen time) needs a small horizontal scroll rather than the alternative of truncating or wrapping any cell — consistent with this app's general "never silently cut off data" stance. If a 6th column is ever added here, expect to revisit both the `min-w` values and the panel/map column-span split again.

### Analytics/forecast additions on top of existing modules
A few features were added as new methods on existing interfaces rather than new modules — worth knowing they exist before re-deriving similar logic:
- `tankolasInterface::getFogyasztasElemzes()` — fuel-consumption anomaly detection. Uses **median**, not mean, as the per-truck baseline — a mean is skewed by a single genuine outlier reading, which would falsely flag every normal reading as anomalous too.
- `koltsegInterface::getTervezettKarbantartasBecsult()` — estimated upcoming maintenance cost, folded into `getVarhatoEredmeny()`'s (forecast P&L) breakdown. The flotta-wide average maintenance cost is computed as **two separate SELECTs summed/averaged in PHP**, not a `UNION ALL` — this project's custom SQL linter disallows `UNION` as well as `JOIN` (discovered mid-implementation; the linter warning was a real hit here, unlike the frequent false-positives that trigger on the substring "JOIN" appearing inside unrelated Hungarian comment text).

### MOL üzemanyagkártya PDF import (`backend/interface/molTankolasInterface.php`)
Admin feltölti a MOL "Számla melléklet" nevű, tranzakció-szintű PDF-részletezőt (NEM magát a számlát) — a Pénzforgalom oldal "MOL tankolás import" gombja nyitja a review-modalt, ugyanaz a "digest, admin dönt" kétlépéses minta, mint a Bank/NAV import (`elemezMolTankolasPdf` → előnézet, `alkalmazMolTankolas` → tényleges INSERT csak jóváhagyás után).
- **PDF→szöveg: `pdftotext -layout` (poppler-utils bináris, `exec()`-kel hívva), NEM composer-csomag** — ez a projekt konvenciója szerint egyetlen PHP-függőség sincs, és egy PHP-natív PDF-parser bevezetése nagyobb kockázat lett volna, mint egy már telepített rendszer-bináris meghívása. **Ez éles deploy-kockázat, amit ez a fejlesztői környezet nem tud leellenőrizni**: ha a production PHP-hoston nincs `pdftotext`/poppler-utils telepítve, `MolTankolasInterface::pdfSzovegKinyerese()` `null`-t ad vissza, és `elemezPdf()` egy egyértelmű, a felhasználónak megjelenő hibaüzenettel tér vissza (`success:false`) — sosem fatal hibával —, de a funkció ott ténylegesen nem fog működni, amíg valaki nem telepíti a binárist a szerverre.
- **Sorok kinyerése**: kártyaszám/rendszám-blokkonként (`Kártyaszám: X Rendszám: Y` fejléc-sorok), tranzakciónként 2 sorból (adatsor + helyszín/termék-név sor) — a `pdftotext -layout` oszlop-igazítását kihasználva, egy termék-kategória horgony (`DIESEL`/`AD BLUE pump`/`OTHER`) körül parse-olva, mert a MOL-sorok szerkezete kategóriánként eltérő oszlopszámú (pl. az "OTHER"/éves kártyadíj sorból hiányzik a "Bruttó listaár" oszlop). Csak a liter-mértékegységű (`ME='L'`) sorok kerülnek be a `tankolasok` táblába — a darabszámra menő tételek (éves kártyadíj) kimaradnak.
- **Km-óraállás placeholder-szűrés**: a MOL km-oszlopában "," és néhány (1-3 jegyű, pl. "0"/"1") érték is megfigyelt, megbízhatatlan "nincs olvasat" jelzés, nem valódi óraállás (élő mintaadaton megerősítve: egy jármű egymást követő tankolásainál "1" majd "379161" szerepelt) — csak a ≥1000 értékű, tisztán numerikus km kerül be, minden más `NULL`.
- **Rendszám↔jármű egyeztetés**: a PDF-ben szereplő rendszámot (pl. "RLP018") és a `kamion`/`furgon` táblák `rendszam` oszlopát is csak alfanumerikus, nagybetűs formára hozva ("RLP018" ⇄ "RLP-018") hasonlítjuk össze — a kötőjel/szóköz írásmódja a két oldal közt gyakran eltér. Fel nem ismert rendszámú sornál a frontend egy sárga jelzésű `<select>`-et ajánl fel a jármű kézi kiválasztására; enélkül a sor nem importálható (a "Import" checkbox letiltva marad).
- **De-duplikáció: `tankolasok.mol_slip_id`** (a MOL "Slip ID" oszlopa, tranzakciónként egyedi), `UNIQUE KEY (admin, mol_slip_id)`, NULL a kézi (sofőr-önkiszolgáló) tételeknél — ugyanaz a "több NULL nem ütközik" minta, mint a `user.email`-fixnél. Ez a tényleges védelem egy PDF véletlen kétszeri feltöltése ellen, `elemezPdf()` is ez alapján jelöli meg előre a "Már importálva" sorokat, `alkalmaz()` pedig a `UNIQUE KEY` ütközést (`PDOException` code 23000) is elkapja védekező jelleggel.
- **`tankolasok.sofor_id` NULL-ozhatóvá vált** (korábban `NOT NULL` volt) — a MOL-adatból nem derül ki, ki vezetett, ezt kitalálni tilos (ld. "no fake data" konvenció), ezért a MOL-importált sorok `sofor_id`-je mindig `NULL`. Ennek egyetlen következménye: a sofőr-oldali `getTankolasok($sofor_id)` (driver saját tankolás-listája) ezeket a sorokat nem mutatja — ez szándékos, a MOL-import admin-oldali, flotta-szintű adat.
- **Szándékosan NEM ír az `egyeb_koltsegek` (Pénzforgalom) táblába** — csak a `tankolasok`-ba (liter/km-szintű, a meglévő `getFogyasztasElemzes()` ezt olvassa). Oka: `koltsegInterface::getKoltsegOsszesito()` az "Üzemanyag" összesítőt a `tankolasok.osszeg` ÉS az `egyeb_koltsegek` (`kategoria='uzemanyag'`) összegéből **feltétel nélkül összeadja** — ha ugyanannak a MOL-számlának a forint-értéke mindkét táblába bekerülne, az duplán számolná be a kiadást.
- **NAV↔MOL-import összekötés ("hivatkozás" fázis, megvalósítva)**: `NavSzamlaInterface::molTankolasSzamlaszamok($ceg_id)` — `SELECT DISTINCT szamlaszam FROM tankolasok ...` — mindkét helyen bekötve: (1) `lekerdezSzamlak()` minden NAV-tételre kitölti a `mol_tankolasbol_fedve` mezőt (a meglévő `mar_importalva`-tól *külön* jelzés, hogy a felület más szöveggel tudja indokolni: nem azért nem importálható, mert már fent van a Pénzforgalomban, hanem mert a MOL tankolás-import már lefedte), és `importalhato = false`, ha ez a flag igaz — a `Koltsegek.js` NAV modal review-táblázata ez alapján tiltja le a checkboxot/kategória-selectet és "Már fedve (MOL tankolás import)" szöveget mutat az "Állapot" oszlopban. (2) `importalSzamlak()` is újra leellenőrzi szerver-oldalon (defense-in-depth, ugyanaz a minta, mint a `mar_importalt`-nál) — egy elavult kliensállapot sem tud duplikált sort beszúrni. Élőben tesztelve: a `tankolasok`-ba beszúrt teszt-szamlaszám blokkolta az `importalSzamlak()`-ba küldött ugyanolyan szamlaszámú tételt (0 importálva, 1 kihagyva), egy másik, nem fedett szamlaszám viszont normálisan bekerült; a `lekerdezSzamlak()`-ot magát (valódi NAV API-hívást igényel) nem lehetett élesben tesztelni valódi NAV-hitelesítő adatok hiányában ebben a fejlesztői környezetben, ezért a review-táblázat megjelenítését Playwright hálózati mockolással (`page.route()`, a `navSzamlaLekerdezes` válasz szimulálásával) ellenőriztük — ez helyesen megjelenítette a letiltott sort a várt szöveggel.
- **Élőben tesztelve** (nem csak kód-olvasással): a valódi felhasználó által küldött MOL "Számla melléklet" PDF-ekkel (`tankolás.pdf`, 34 tranzakció, 1 nem-üzemanyag sor kihagyva) helyi PHP CLI-vel és Playwright-tal, valódi böngészőn keresztül (session-táblába beszúrt admin-munkamenettel) — a kinyert 33 sor bruttó összegének összege pontosan egyezett a MOL számla-összesítő (`tankolá számla.pdf`) 4 508 594 Ft-os végösszegével, a rendszám-egyeztetés helyesen talált/nem talált jármüvet, a de-duplikáció (ismételt feltöltés/`alkalmaz()` ismételt hívása) helyesen `mar_importalva`/`marVolt`-ként jelölte a már beimportált sorokat, a teszt-sorok utána törölve lettek a helyi DB-ből.
- **Gotcha, amibe menet közben belefutottunk**: a modal `maxWidth="max-w-6xl"` propja az első használata volt ennek az osztálynak a kódbázisban — mivel a `tailwind.css` nincs automatikusan újrafordítva CRA dev szerver alatt (ld. a fájl elején lévő `build:tailwind` megjegyzés), a modal korlátlanul szélesre nőtt, és a review-táblázat "Dátum" oszlopa vizuálisan levágódott. Ez pontosan az a hibaosztály, amire a projekt már korábban is figyelmeztet — Playwright-tal `getBoundingClientRect()`-tel derült ki (a DOM-elrendezés helyes volt, csak a screenshot mutatta hibásnak), a `npx tailwindcss -i ... -o ...` újrafordítás után a modal helyesen a `max-w-6xl` korlátra állt.

### Deviza (multi-currency) handling in Pénzforgalom
`egyeb_koltsegek` gained `deviza`/`eredeti_osszeg`/`arfolyam` columns, but **`osszeg` remains the single source of truth every report aggregates** — it's always HUF, computed and **frozen** at entry time from that moment's MNB rate. The other three columns are informational-only ("what was actually typed, at what rate") and are **never** recomputed against a later, current rate — this was a deliberate design choice specifically so `koltsegInterface.php`'s existing aggregation SQL (`getKoltsegOsszesito`, etc.) needed **zero changes**, and so a historical report doesn't silently drift as exchange rates move over time.
- **Currency list**: `listaelemek` gained a `'deviza'` `tipus` (same generic per-company list mechanism as `kamion_meret`/`bejelentes_tipus`/etc., ld. `listaInterface.php` `TIPUSOK`), with a **dedicated admin page** (`src/views/admin/Devizak.js`), not a tab inside the generic `Listak.js`. This is deliberate: `Listak.js`'s add-item flow slugifies a free-typed display name into the storage key (`"Kamion méret"` → `kamion_meret`), which is wrong for currencies — the key must be a real, uppercase ISO 4217 code (`EUR`) for the MNB rate lookup to match, not a lowercased slug. `Devizak.js` takes an explicit Kód (forced-uppercase, 3 chars) + Név instead. HUF is seeded `vedett` (protected, undeletable — it's the base/reporting currency); EUR/USD are pre-seeded but deletable.
- **Rate source**: `piaciArakInterface::getArfolyam($devizanem)` — a public method reusing the *same* cache-or-fetch-from-MNB mechanism as the sidebar's EUR/USD widgets (`frissitVagyOlvas()`), but generalized to **any** MNB-quoted currency code, not just the two hardcoded sidebar entries. `koltsegInterface::resolveDevizaOsszeg()` calls it via `global $piaciArakInterface;` (the same cross-interface global-reference pattern `ApiHandler::getEsemenyek()` already uses for `$fuvarInterface`) — no ApiHandler wiring changes were needed for this feature at all, since it reuses 100% pre-existing actions/globals.
- **NAV Online Számla already handled multi-currency correctly before this feature existed** — NAV's own digest response is legally required to include a HUF-equivalent for every invoice regardless of its billing currency (`invoiceNetAmountHUF`/`invoiceVatAmountHUF`), computed by NAV itself at the invoice's issue-date rate, so `navSzamlaInterface.php` never actually excluded or blocked non-HUF invoices. What this feature added on the NAV side: the digest's *original*-currency amount (`invoiceNetAmount`/`invoiceVatAmount`, confirmed present via a live probe) is now also captured, so an imported foreign-currency invoice populates `deviza`/`eredeti_osszeg` too (with `arfolyam` back-computed from NAV's own HUF figure — deliberately **not** a fresh MNB lookup, since NAV's rate for that specific invoice date is more authoritative than today's rate for a historical transaction).

### Removed: Fuvarok / Fuvartervező modules (and fuvar-linked payment tracking)
A `fuvarok` table and matching Fuvarok (list) + Fuvartervező (drag-and-drop dispatch calendar, `react-big-calendar`) admin pages existed at one point, plus a follow-on "kifizetve" (paid/unpaid) flag on each fuvar and a `getUgyfelKintlevoseg()` customer-receivables report built on top of it. **All of this was deliberately removed** (routes, sidebar nav, `fuvarInterface.php`, the `fuvarok`-sourced revenue queries in `koltsegInterface.php`, the `jogosultsagInterface.php` module entry, the `ugyfelek.fizetesi_hatarido_nap`/`fuvarok.kifizetve*` columns) after a product discussion concluded that freight jobs and payment terms in this business are actually negotiated verbally (phone calls), so structured records for them were never reliably kept up to date — a receivables/forecast feature built on data nobody maintains is worse than not having it, since it looks authoritative while actually being wrong. `ugyfelek` (customer contact records — name/address/tax id) was deliberately **kept** as a standalone module; only the fuvar-linked and payment-term parts went. **Consequence for Pénzforgalom**: `koltsegInterface::getKoltsegOsszesito()`'s "Bevétel" (revenue) is now sourced **entirely** from manually-entered/NAV-imported `egyeb_koltsegek` rows with `irany='bevetel'` — there is no automatic revenue source left in the schema. If a future "how much revenue" feature is requested, do not resurrect the old `fuvarok`-based auto-revenue approach without re-confirming the verbal-agreement problem has actually changed. `Naplo.js`'s `TABLA_LABEL.fuvarok: "Fuvar"` was deliberately left in place (not dead code) — historical audit-log rows with `tabla='fuvarok'` from before the removal still exist and need a friendly label to render.

### UX-audit consistency pass
A full-app UX/IA audit (professional "market intelligence dashboard" bar — clarity, hierarchy, semantic color, no decorative noise) led to several cross-cutting consistency fixes, all still in force as conventions for future pages:

### Mobile calendar (Dashboard)
`components/Cards/CardCalender.js` branches its entire render on `isMobile` (via `react-responsive`), not just CSS: on mobile it shows a month-grid-only `react-big-calendar` (`views={["month"]}`, no other views, so the view-switch buttons don't even render) with `selectable="ignoreEvents"` + `onSelectSlot`/`onDrillDown` both wired to a single `setSelectedDate` — this is deliberate, since providing `onDrillDown` fully replaces RBC's default "navigate to Day view" behavior, keeping the calendar pinned to month view forever. ### Mobile forms (no popup)
`components/UI/Modal.js` branches on `isMobile` too: desktop keeps the classic fixed-overlay dialog; mobile renders the same content as a **plain in-flow card** (no backdrop, no `fixed`) at whatever point in the JSX tree the call site puts `<Modal>` (all 4 current call sites — Karbantartasok, CardTableForEsemenyek, CardTableForTervezettKarbantartasok, CardTableForPotkocsiTervezettKarbantartasok — put it after their table/list, so opening it means scrolling down; a `scrollIntoView` on open compensates for that).

**Non-obvious browser gotcha hit while building this, and how the final fix is actually structured** — worth reading before touching mobile bottom-clearance again:
- A trailing `margin-bottom` on the last in-flow child of a scrolling container is *not* counted in that container's `scrollHeight` (browsers exclude margins from the scrolling-area box calculation). `mb-6`, `mb-24`, even `mb-96` on a trailing element all produce the *exact same* `scrollHeight` — margin never fixes this, no matter how big.
- A **real sibling block with an explicit height** (e.g. `<div className="h-20" />`, not padding/margin) placed directly after the content that might overflow is what actually reserves usable scroll space — but *only* if it's added **inside the same box whose content might overflow**.
- That "inside" qualifier matters because of a second, separate quirk: page roots built with `h-full` + `flex-col` (used deliberately on Dashboard.js and Karbantartasok.js so DataTable/CardCalender can fill remaining vertical space when content is short) **cap their own rendered height** at the parent's height when `overflow` is left at the default `visible` — so a sibling spacer placed *outside* that box (e.g. a global one in `layouts/Admin.js`, after `<Switch>`) never gets pushed down by that box's own overflow and does nothing for it.
- Net result — **two separate fixes, both still in place, each covering a different page shape**:
  1. `layouts/Admin.js` has a real spacer block (`h-20`, `md:hidden`) right after `<Switch>` — covers "natural flow" pages with no `h-full` root (KamionForm, PotkocsiForm, SoforForm, BejelentesekForm, Settings, and any list page whose `DataTable` isn't in `fill` mode).
  2. Pages whose own root is `h-full flex-col` (Dashboard.js, Karbantartasok.js) additionally carry their **own** trailing spacer *inside* that root — Karbantartasok.js gets one for free from `Modal.js`'s mobile branch (it renders as a `<>`-wrapped sibling next to the card, so it lands inside Karbantartasok's own root), Dashboard.js has an explicit one of its own after the calendar card.
  - If a new `h-full`-rooted mobile page ever has its bottom content clipped by the nav bar again, the Admin.js-level spacer will *not* fix it — add a same-pattern spacer inside that page's own root instead.

### Floating popovers (`components/UI/DatePicker.js`)
The custom calendar dropdown used by every `type="date"` `FormField` renders via `ReactDOM.createPortal(..., document.body)` with `position: fixed` coordinates computed from `getBoundingClientRect()` on open — it does **not** use a plain `absolute` child of its trigger button. This is deliberate, not incidental complexity: an `absolute`-positioned popover nested inside a scrollable container (any `Modal.js` body, any `overflow-y-auto` list) gets silently clipped at that ancestor's edge once it needs to render outside it, which is exactly what happens for a date field near the bottom of a form — the calendar's own bottom (or top, when flipped upward) gets cut off. Portaling to `document.body` with `position: fixed` escapes every ancestor's `overflow`/stacking context, so the panel is always fully paintable regardless of where the field sits.

Same-direction-flip logic still applies (`openUpward` when there isn't `~380px` below the field), now computed once into `top`/`bottom` fixed-pixel coordinates rather than CSS `top-full`/`bottom-full` classes. Two things worth knowing if this file needs touching again:
- **Don't add a scroll/resize listener that recomputes or closes the panel.** It was tried and reintroduced flakiness — Playwright (and likely real browsers) fire spurious `scroll` events from a clicked element's native "scroll into view" adjustment, and recomputing mid-scroll can visually misplace the panel for a frame; closing on scroll made it vanish immediately on some clicks. Position is computed once on open and left alone; click-outside-to-close (checking both the trigger's and the portaled panel's ref, since the panel is no longer a DOM descendant of the trigger once portaled) is enough.
- If you ever debug "the picker opens in the wrong place" via a screenshot again: check whether it's actually the intentional upward-flip (a field near a container's bottom edge legitimately opens a tall panel that visually spans up past *other* fields above it — that's correct floating-dropdown behavior, not a bug) before assuming a positioning regression.

### PWA (installable app)
Full PWA support was added: `public/manifest.json` (proper `icon-192.png`/`icon-512.png`/`icon-maskable-512.png`, all generated locally with ImageMagick — a solid-brand-blue square with an "ST" monogram, since no square app-icon asset existed in the repo, only the wide wordmark `logo.png`/`logo.svg`), `public/apple-touch-icon.png`, iOS-specific meta tags in `public/index.html`, and `src/components/PWA/InstallPrompt.js` (mounted globally in `src/index.js`, outside the router `<Switch>` so it shows on every route) which handles the Chrome/Android `beforeinstallprompt` flow and shows a manual "Add to Home Screen" hint on iOS Safari (which never fires that event).

The actual offline/precache behavior comes from `src/service-worker.js` — **this file's mere existence is what matters**: `react-scripts`' webpack config conditionally adds `WorkboxWebpackPlugin.InjectManifest` only `isEnvProduction && fs.existsSync(swSrc)` (`swSrc` = `src/service-worker.js`). All the `workbox-*` packages it imports (`workbox-core`, `workbox-precaching`, `workbox-routing`, `workbox-strategies`, `workbox-expiration`) are already transitive dependencies of `react-scripts` — nothing extra was installed. `src/serviceWorkerRegistration.js` (pre-existing CRA scaffolding) was already wired up correctly in `src/index.js` (`serviceWorkerRegistration.register()`) but had nothing to register before this, since no `service-worker.js` existed — the registration silently 404'd in every prior production build.

The service worker only activates in production builds served over `https`/`localhost` (`process.env.NODE_ENV === "production"` gate inside `serviceWorkerRegistration.js`) — it will never register under `npm start`. To verify PWA behavior locally: `npm run build`, then serve `build/` statically (e.g. `npx serve -s build -l 4173`) and check `navigator.serviceWorker.getRegistrations()` / DevTools Application tab from there, not from the dev server.

A critical UX/UI pass on the driver-facing (`layouts/User.js` + `views/user/*.js`) mobile experience, driven by the principle "a sofőrnek ne kelljen gondolkodnia — egy pillantásból értse, mit lát". Concrete, reusable outcomes:

Set `mobileColumns={2}` only on sections where every field is uniformly short (numbers/dates) — `Tankolas.js`'s single section, `Profil.js`'s "Felhasználó adatok"/"Iratok". **Deliberately left at the default on `Profil.js`'s "Kapcsolat" section** — it mixes short fields (Város/Irányítószám) with long ones (Cím/Lakcím, `md:col-span-2`), which would look broken paired 2-up on a narrow screen. Reuse this prop rather than inventing a new pattern for any future "these mobile fields are all short, pair them up" case.
- **`BejelentésUj.js` (create-report flow)**: the Prioritás field and the "Sérülés"/"Baleset" type options were removed from the driver-facing creation screen specifically (not from the underlying `listaelemek` admin-configurable list, not from historical records) — filtered client-side via `REJECTED_TIPUSOK`. The backend already defaulted `prioritas` to `'kozepes'` when absent (`bejelentesekInterface.php`), so no backend change was needed; an admin can still set/edit priority afterward via `CardBejelentesek.js`. Priority badges were also removed from the driver's own list/detail views (`Dashboard.js`, `Bejelentesek.js`) since the field is no longer driver-facing at creation time and showing a badge no one chose is more confusing than informative.
- **`Bejelentesek.js` card hierarchy**: presence of an admin response (`b.admin_valasz`) is now surfaced immediately next to the status badge (a small green "Válaszolt" pill) rather than only visible after scrolling past the description — a driver can tell at a glance whether a report has been answered.
- **`Ertesitesek.js` read/unread tracking**: purely client-side, via `localStorage` key `sofor_ertesitesek_latott_${user.id}` (never the server — this is a personal "have I seen this" marker, not app state). Item ids are prefixed by category (`doc-`/`bej-`/`jv-`) to avoid collisions across the three notification sources `useSajatErtesitesek.js` returns. The "new" set for a given page view is computed against the *previous* visit's stored ids (captured before overwriting storage with the current visit's full id list), so the red dot indicator is visible for the whole visit and only clears on the *next* open — not disappearing mid-view. If a similar unread-marker is ever needed elsewhere, follow this same snapshot-before-overwrite pattern.
- Other small consistency fixes from the same pass, no new pattern beyond "do the obvious fix": `BejelentesUj.js`'s save button moved from a `fixed` bottom bar back into normal document flow (the fixed bar left an empty gap once Prioritás was removed and the form got shorter); `MobileHeader.js`'s back button grew from 36px to 44px (Apple HIG/Android minimum tap target); the duplicate "Bejelentés" tile was removed from Dashboard's Gyors műveletek grid (the BottomNav's always-red FAB already covers it); the "Jóváhagyásra vár: {rendszám}" text on Dashboard's vehicle cards, which used to silently truncate mid-plate-number in a `text-[11px]` label, was shortened to just "Vár jóváhagyásra" (the driver already knows which vehicle they requested); `Helyszinek.js` shows a one-line hint pointing at the `+` button when the (unfiltered) list has ≤2 items, so a near-empty list doesn't read as a dead end.

For headless verification of a **driver** (`sofor`) session specifically (as opposed to the admin pattern below): the `sessions` table needs a row with `felhasznalo_tipus = 'sofor'`, `felhasznalo_id` = the `user.id`; the `sessionStorage` shape mirrors exactly what `loginUser` returns and what `Login.js` stores (`sessionStorage.setItem('user', JSON.stringify(result.user))` + `sessionStorage.setItem('sessionToken', result.token)`), i.e. the full driver row (`id`, `admin` = owning admin id, `name`, `email`, `kamion`, …), not a synthetic `{ id, name, admin: true }` object — that shape is for admin-side verification only (see below) and won't satisfy driver-facing pages/actions that expect real driver fields.

**`scripts/prerender.js` mostantól automatikusan lefut minden `npm run build` után** (2026-07-17, SEO-audit nyomán bevezetve) — `package.json`-ban egy `"postbuild": "node scripts/prerender.js"` hook hívja, és a `playwright-chromium` valódi `devDependency`-ként szerepel (nem `--no-save`-del, kézzel telepítve), hogy egy friss `npm install` (amit a `genezio.yaml` a deploy során lefuttat) is megkapja. Mivel a `genezio.yaml` deploy-szkriptje is `npm run build`-et hív, ez a lépés **az éles deploy során is automatikusan lefut**, nem csak lokálisan — élőben, `build/<route>.html`-ben ellenőrizve valódi H1-et, oldal-specifikus `<title>`/`canonical`-t és a `FAQPage`/`BreadcrumbList` JSON-LD-t tartalmaz minden route-on.

**Fail-safe tervezés, mert a genezio build-szerverén nem garantált a headless Chromium támogatása**: a script SOHA nem lép ki nem-nulla kóddal — hiányzó csomag, böngésző-indítási hiba vagy egy adott route renderelési hibája esetén is csak figyelmeztetést ír ki és `exit(0)`-val tér vissza (élőben letesztelve: a `playwright-chromium` modul szimulált hiányában is 0-s exit kóddal, hibaüzenettel állt le). Legrosszabb esetben a build a szokásos, előrenderelés nélküli állapotban marad — ez nem regresszió, csak elmaradt javítás egy adott build-nél, sose buktatja el a teljes deployt. Ha ez a garancia valaha megváltozik (pl. valaki `process.exit(1)`-re módosítja a hibaágakat), az visszahozza a korábbi kockázatot, hogy egy Chromium-indítási hiba az egész genezio deployt elbuktatja.

**GOTCHA — a prerenderelt route-ok LAPOS `.html` fájlok (`build/belfoldi-fuvarozas-arajanlat.html`), NEM alkönyvtárak (`build/belfoldi-fuvarozas-arajanlat/index.html`)** — ez utóbbi volt az eredeti, első nekifutásra logikusabbnak tűnő megoldás, de élesben (2026-07-17, valódi Apache-példányon egyeztetve, nem csak feltételezve) **301-es végtelen redirect-mintát** okozott minden aloldalon: Apache mod_dir-je egy valódi könyvtárra mutató, per nélküli URL-t (pl. `/belfoldi-fuvarozas-arajanlat`) alapból átirányít a per-jeles verzióra, ami eltér a `sitemap.xml`/canonical/OG tagekben szereplő formától. Ezt **sem** a `DirectorySlash Off` (mod_dir), **sem** egy könyvtár-alapú `.htaccess` `RewriteRule` (`RewriteCond -d` + `RewriteRule ^(.*[^/])$ $1/index.html`) nem tudta megkerülni ezen a hoszton — mindkettőt lokálisan, egy a hoszttal megegyező `AllowOverride FileInfo`-only Apache-példányon leellenőriztem, egyik sem oldotta meg (a hoszt `AllowOverride`-ja nem ad `Indexes` kontextust a `DirectorySlash`-hoz, a könyvtár-alapú `RewriteRule` pedig ezen a hoszton később fut le, mint mod_dir saját átirányítás-logikája). A szándékolt fix: `scripts/prerender.js` lapos `<route>.html` fájlba ír (nem alkönyvtárba), és a `.htaccess` egy `RewriteCond %{REQUEST_FILENAME}.html -f` + `RewriteRule ^(.*)$ $1.html [L]` szabállyal képezi le a kiterjesztés nélküli URL-t erre — mivel a route sosem lesz valódi könyvtár a lemezen, mod_dir-nek nincs mit átirányítania.

**⚠️ EZ A FIX A KÓDBAN HELYES, DE ÉLESBEN (2026-07-17, egy SEO-audit során futtatott `curl -I` sorozattal ellenőrizve) A 7 ÉRINTETT URL MÉG MINDIG 403 FORBIDDEN-T AD** a kanonikus (per nélküli) címén — csak a nem-kanonikus, trailing-slash-es változat szolgál ki tartalmat (200). Legvalószínűbb ok: a **korábbi, alkönyvtár-alapú deploy maradvány-könyvtárai még mindig ott vannak a szerver docroot-jában**, és beárnyékolják az új lapos fájlokat (a per nélküli kérésnél Apache a meglévő könyvtárba ütközik, még mielőtt a `.htaccess` szabály lefutna — ugyanaz a "mod_dir előbb fut le" jelenség, ami a 301-es problémát is okozta —, és mivel `DirectorySlash Off` van beállítva, 403-at ad redirect helyett). **Ez fájlrendszer-szintű, szerveroldali probléma, amit a repóban lévő kód önmagában nem tud javítani** — a docroot-ot SSH-val kézzel át kell nézni, a régi `<route>/` könyvtárakat törölni kell (vagy a deploy-folyamatot kell tiszta-wipe-osra állítani additív feltöltés helyett), majd `curl -sI`-vel, **trailing slash nélkül**, mind a 8 sitemap URL-t újra le kell ellenőrizni. **Ha valaha megint alkönyvtár-alapú megoldás merülne fel (pl. egy jövőbeli SSR-migráció kapcsán), mindig ellenőrizd élőben `curl -sI`-vel — ez a hibaosztály csendben, HTTP-szinten jelentkezik, JS-t futtató böngészőből (ami követi a redirectet, vagy a régi tartalmat mutatja a slash-es változatról) észrevétlen marad.**

**Teljes SEO-audit (2026-07-18) és az azóta javított hibák**: egy élő (`curl`-alapú) + forráskód-audit két, korábban nem dokumentált problémát talált. (1) **Az éles deploy elavult volt**: a fenti 403-as gotcha miatt a production docroot 7 aloldala (a főoldal kivételével mind) a `priceRange`-javítás és a `Service`-séma bevezetése ELŐTTI, elavult `LocalBusiness` JSON-LD-t szolgálta ki (érvénytelen `priceRange` mezővel, `@id` és `Service`-séma nélkül), és a forráskódba visszakerült "a referenciák minta-szövegek" disclaimer sem látszott élesben — helyi `npm run build && node scripts/prerender.js` futtatással megerősítve, hogy ez **kizárólag deploy-elavulás**, nem kód-hiba volt: egy friss build minden route-on helyesen tartalmazza mindkettőt. **Ez rávilágít, hogy a fenti 403-as/301-es gotcha-nak van egy csendes, HTTP-státusztól független tünete is** — egy adott route 403/301 nélkül, 200-cal is szolgálhat ténylegesen elavult tartalmat, ha a szerveren maradt régi fájl/könyvtár a `.htaccess` rewrite-nál korábban fut le. (2) **`public/.htaccess` valódi hibákat javítottunk**: a korábbi feltétel nélküli catch-all (`RewriteCond !-f !-d` + `RewriteRule . /index.html`) minden érvénytelen URL-re `200`-at adott a főoldal `index,follow` tartalmával (soft-404, láthatatlan minden JS-t nem futtató crawler — Googlebot nyers lekérés, GPTBot, ClaudeBot, PerplexityBot — számára) — ezt egy explicit, csak a ténylegesen létező route-prefixekre (`admin`/`user`/`auth`/`profile` + a 7 statikus oldal) szűkített szabálypár váltotta fel, minden más útvonal most valódi Apache 404-et kap. Eközben, helyi Apache-példányon (`AllowOverride All`, mod_rewrite `LogLevel debug rewrite:trace6`) tesztelve kiderült, hogy **a lapos-fájlos flat-rewrite rule (`RewriteRule ^(.*)$ $1.html [L]`) önmagában is hibás volt**: egy prerenderelt route alá írt, nem létező alútvonalra (pl. `/belfoldi-fuvarozas-arajanlat/barmi`) a `.*` minta + `%{REQUEST_FILENAME}.html -f` feltétel miatt mod_rewrite saját "path info" heurisztikája tévesen igaznak értékelte a feltételt (mert `belfoldi-fuvarozas-arajanlat.html` létezik), ami minden körben egy újabb `.html`-t fűzött a végére — végtelen belső-redirect hurkot és HTTP 500-at okozva. Élőben ez jelenleg **nem** látszik (mert a régi, 403-as gotcha-ban leírt maradvány-könyvtárak még ott vannak a szerveren, és elfedik ezt a hibát is), de a maradvány-könyvtárak SSH-s törlése után azonnal jelentkezne, ha a mintát nem szűkítettük volna `^([^/]+)$`-ra (egyetlen útvonal-szegmens) — ez most már javítva van. Emellett alapvető biztonsági response headerek (HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy) és egy `public/llms.txt` is bekerült. **Mindhárom .htaccess-fix helyi, valódi Apache-példányon (`apache2 -f <config> -k start`, saját portra, root nélkül) le lett tesztelve** 9 forgatókönyvön (ismert route, ismeretlen route, nested érvénytelen útvonal, admin-alútvonal, hiányzó prerender fail-safe, biztonsági headerek, JS cache-headerek) — ez pótolja azt, hogy CRA dev szervere/`serve` nem értelmezi a `.htaccess`-t, tehát böngészőből nem lett volna ellenőrizhető. **Amit ez a session NEM tudott elvégezni** (szerver SSH-hozzáférés hiányában, ld. "Local dev environment" lentebb): a production docroot tényleges tiszta redeploya és a régi maradvány-könyvtárak törlése — eddig csak a forráskód (és a helyi build/prerender-teszt) igazolja, hogy a javítások helyesek, az éles szerveren még nincsenek élesítve.

Megoldás: a kártya maga már NEM link, csak a cím (`h3`-on belüli `<Link>`) — a teljes kártya kattinthatóságát egy CSS "stretched link" trükk adja (`after:content-[''] after:absolute after:inset-0` a linken + `relative` a kártyán). **Gotcha, amibe bele lehet futni**: `after:absolute`/`after:inset-0` önmagában NEM elég — Tailwind `before:`/`after:` variánsai csak akkor generálnak tényleges pszeudo-elemet, ha a `content` is explicit be van állítva (`after:content-['']`); enélkül a böngésző computed style-ja `content: none`-t ad, a pszeudo-elem nem is létezik, és a link csak a szöveg saját (kis) területén kattintható — ezt csak élő Playwright-teszttel (`getComputedStyle(el, '::after')` + tényleges egérklikk a kártya leírás-szövegén, nem csak a linken) sikerült elkapni, `npm run build:tailwind` újrafuttatása után. **Amit a lista alapján szándékosan NEM módosítottunk**: az ismétlődő anchor-szövegek (pl. "Kezdőlap"/"Rólunk"/"Kapcsolat"/"Bejelentkezés" a nav+footer+mobil-nav között, a telefonszám és az "Adatvédelmi tájékoztató" footer-linkek) — ezek különböző, legitim UI-elemek (nav vs. footer vs. jogi sáv) konzisztens, azonos célra mutató szövegei, mesterséges változatossá tételük UX-romlás lenne valós SEO-haszon nélkül. A "web server verzió szerepel a HTTP fejlécben" találat (`Server: Apache/2.4.x`) helyi Apache-teszttel megerősítve **nem javítható `.htaccess`-ből** (`ServerTokens`/`ServerSignature`, és a `Header unset/set Server` mod_headers-szel sem hatásos — kipróbálva, a fejléc változatlan maradt) — csak a fő szerver-configból, SSH-hozzáféréssel. A hivatkozó domainek/backlinkek száma (1 domain, 1 link, 1 IP) off-page tényező, kód-módosítással nem befolyásolható.

### Gotcha — kimenő e-mailek mind a 4 típusa spambe ment a `From: agoston@ps.hu` fejléc miatt
Élesben tesztelve (a redesign utáni ellenőrzés során) kiderült, hogy MINDEGYIK kimenő e-mail (ajánlatkérés, jelentkezés, jelszó-visszaállítás, lejárat-cron) a Gmail Spam mappájába érkezett, sosem az Inboxba, annak ellenére hogy a `mail()` PHP-hívás sikert (`true`) jelzett és a `sendEmail()`-ben lévő korábbi hibalogoló ág (`error_log("Email sending failed...")`) sosem futott le — vagyis a levelek ténylegesen elhagyták a szervert, csak a fogadó oldalon minősültek spamnek.
- **Gyökérok, DNS-nyomozással beazonosítva**: a `From` fejléc korábban `agoston@ps.hu` volt (egy, a hosting-szolgáltató/fejlesztői domain címe, amit a szerver SPF-je — `dig TXT ps.hu` — explicit engedélyez erről a szerver-IP-ről). A `ps.hu` domainnek viszont **van egy saját DMARC rekordja `p=quarantine` szabállyal** (`dig TXT _dmarc.ps.hu` → `v=DMARC1; p=quarantine`), miközben a kimenő levelek nincsenek DKIM-mel aláírva. Mivel a `mail()` hívás által használt envelope-from valószínűleg nem egyezik pontosan a `ps.hu` domainnel (DMARC SPF-illesztéshez az envelope-from domainnek és a látható From-domainnek egyeznie kell, nem elég, hogy egy MÁSIK domain SPF-je engedélyezi az IP-t), a DMARC-illesztés elbukik — és a `ps.hu` domain SAJÁT policy-je utasítja a Gmailt (és minden DMARC-ot respektáló fogadót), hogy az ilyen leveleket tegye spambe/quarantine-ba. Ez a policy attól függetlenül lefut, hogy a levél ténylegesen kitől jött — pusztán attól, hogy a From fejléc `@ps.hu`-t mutat.
- **Fix**: a `From` fejléc domainje `agoston@ps.hu`-ról `noreply@szikora-transz.hu`-ra változott (`sendEmail()`, ld. fent) — a `szikora-transz.hu` domainnek **nincs** DMARC rekordja (`dig TXT _dmarc.szikora-transz.hu` üres), és a saját SPF-je (`v=spf1 a mx -all`) explicit engedélyezi ezt a szervert (a domain A rekordja maga ez a szerver-IP). Nincs tehát kényszerítő quarantine-utasítás, amit a Gmailnek követnie kellene, így a levelek sokkal nagyobb eséllyel jutnak el az Inboxba.
- **Ha ez a probléma egy jövőbeli környezetben/domainváltásnál visszatér**: mindig ellenőrizd `dig TXT _dmarc.<From-domain>`-t — ha van rajta `p=quarantine`/`p=reject`, az önmagában elég ok a spambe kerüléshez, függetlenül az SPF-től vagy attól, hogy a `mail()` sikert jelez-e. A tényleges javítás vagy a From-domain cseréje egy DMARC-mentes/lazább policy-jű, a küldő infrastruktúrához illeszkedő domainre, vagy (hosszabb távon, ha a spam-probléma visszatérne) DKIM-aláírás bekötése a szerver oldalán a ténylegesen használt From-domainhez.

### Furgon (van) — third, self-propelled fleet vehicle type (full parity with kamion)

A third vehicle category was added alongside `kamion`/`potkocsi`, at the user's explicit request for **full functional parity with kamion** (own adatlap, maintenance history, GPS tracking via GPSmart, fuel log, financial linkage in Pénzforgalom, driver assignment/vehicle-switch requests) — not just a registry entry. A furgon is **self-propelled, like a kamion** (not a towed trailer like `potkocsi`), so it has no `potkocsi`-style towing column and doesn't appear in GPSmart-only-kamion-era code paths without an explicit new branch.

**The general pattern used throughout**: everywhere the codebase already treats kamion/potkocsi as a connected pair (`kamion_id`/`potkocsi_id`, e.g. Pénzforgalom cost linkage, `karbantartasokInterface.php`), furgon became a **third, sibling branch** in the same pattern (3-way ternary/UNION/select). Everywhere something was previously **kamion-only** because potkocsi has no engine/driver (GPSmart tracking, tankolás, sofőr-hozzárendelés, jármű-váltási kérés), furgon became a **new second branch alongside kamion** (not a 3-way — potkocsi still doesn't participate in these).

**Backend**: `backend/interface/furgonInterface.php` is a near-literal mirror of `kamionInterface.php` (minus the `potkocsi` FK / `potkocsiRendszamFeloldas()` helper), wired into `ApiHandler.php` the standard 3-step way (require + instantiate + add to the `global $kamionInterface, $potkocsiInterface, $furgonInterface, ...;` list inside `process()`). `furgon`/`furgon_karbantartars` are literal mirrors of `kamion`/`kamion_karbantartars`. Extended for the third branch: `karbantartasokInterface.php::getKarbantartasok()` (3rd UNION ALL branch + `getFurgonKarbantartas`/`updateFurgonKarbantartas`/`deleteFurgonKarbantartas`), `koltsegInterface.php` (most invasive — furgon breakdown in `getKoltsegOsszesito()`, `getBiztositasKiadasok()`, `getTervezettKarbantartasBecsult()`, `furgon_id` column on `egyeb_koltsegek`), `listaInterface.php` (new `furgon_meret` list type — furgon size categories differ from kamion's, so **not** a reuse of `kamion_meret`; `jarmu_allapot`/`biztositas_utem` extended with a furgon entry since those states genuinely apply the same way), `jogosultsagInterface.php` (`'furgonok' => ['hozzaferes','szerkesztes','torles']` module), `keresesInterface.php`/`GlobalSearch.js` (global search now also matches furgon rendszám). **Two real schema bugs were found and fixed during implementation** (both empirically verified against the live local DB, not just reasoned about — see the durable comments left in `backend/sql/28.sql` at each fix site):
1. **`gpsmart_napi_km`'s original nullable `kamion_id`/`furgon_id` pair design was wrong**: MySQL/MariaDB never treats two `NULL`s as equal for `UNIQUE KEY` duplicate-detection, so `INSERT ... ON DUPLICATE KEY UPDATE` against a nullable pair silently inserted a **new duplicate row** on every write instead of updating, which would have double-counted `SUM(km)` in the Ft/km financial report. Fixed by replacing the nullable pair with a single, always-`NOT NULL` `jarmu_tipus ENUM('kamion','furgon')` + `jarmu_id INT` pair and `UNIQUE KEY (jarmu_tipus, jarmu_id, datum)`.
2. **`jarmu_valtas_kerelmek.tipus` turned out to already be a hard `ENUM('kamion','potkocsi')`** (a prior research pass had assumed it was a free string, since the PHP code treats it that way). Inserting `'furgon'` into a MySQL non-strict-mode ENUM column with an unlisted value silently stores an **empty string**, not an error — this corrupted the request's `tipus` and broke rendszám resolution (`getRendszamok()`-based lookup matched no branch) without any visible error until live-tested end-to-end. Fixed by `MODIFY COLUMN tipus enum('kamion','potkocsi','furgon') NOT NULL`. **General lesson reinforced**: an ENUM's actual definition should be checked (`SHOW COLUMNS`), never assumed from how permissively the PHP layer treats the value — this exact failure mode (silent empty-string coercion, no thrown error) is easy to miss without a live end-to-end test.

**Frontend key-collision gotcha, fixed in three places**: any list that groups/keys data by `kamion_id` alone breaks once furgon rows are mixed in, because a furgon row's `kamion_id` is `null` (its own id lives in a separate `furgon_id` field) — multiple furgon rows then collide on the same `undefined`/`null` React key or map key. Fixed by switching to a composite `` `${jarmu_tipus}:${id}` `` key in `CardUzemanyagElemzes.js` (toggle/grouping state), `Flottakovetes.js` (the `megtettUtMa` lookup map built from `gpsmartMegtettUtMa`'s response), and `KihasznaltsagiModal.js` (table row `key`). Any future code that consumes a `kamion_id`/`furgon_id`-pair API response (`getFogyasztasElemzes`, `lekerdezMegtettUtMa`, `getKihasznaltsagiRiport`, `lekerdezPoziciok`) needs the same composite-key treatment if it keys/groups by vehicle.

**Frontend**: full admin CRUD mirroring the kamion module (`Furgonok.js`/`FurgonForm.js`/`CardFurgon.js`/`CardFurgonAdatokForm.js` [no Pótkocsi select] /`CardFurgonFajlok.js`/`CardTableForFurgonok.js`, plus `CardFurgonEsemenyekForm.js` + `src/components/Table/furgon/CardTableForFurgon{Elvegzett,Tervezett}Karbantartas{,ok}.js` mirroring the potkocsi-specific table components — **note**: these `CardXEsemenyekForm`/karbantartás-tab components are wired up but, matching pre-existing kamion/potkocsi behavior, **the tab button that would reach them was never added to `CardKamion.js`/`CardPotkocsi.js`/`CardFurgon.js`** — this is dead/unreachable code inherited from the existing convention, not a furgon-specific bug; the real, live maintenance-CRUD path is the standalone `Karbantartasok.js` page). ## MOL tankolás-import sorok a Tételek listán (2026-07-21)

## Tachográf kártya (.ddd) import (2026-07-23)

Új, admin-only modul: a sofőr digitális tachográf-kártyájának letöltött fájlját (`.ddd`, EU digitális tachográf szabványos bináris export) az admin tölti fel (`src/views/admin/Tachograf.js`, "Csapat" nav-csoport), a rendszer napi vezetési/pihenő időt és a felhasznált járműveket dekódolja és riportálja. Ugyanaz a "digest, admin dönt" kétlépéses import-minta, mint a NAV/Bank/MOL importoknál.

- **`backend/DddParser.php`** — tiszta, DB-független bináris dekóder (nincs composer-függőség, ugyanaz az elv, mint `CborDecoder.php`/`WebAuthnHelper.php`-nél). A `.ddd` blokk-keretezés (`2 bájt FID + 1 bájt típus (0/2=adat gen1/gen2, 1/3=aláírás) + 2 bájt hossz + payload`) és az alábbi FID-ek **egy valódi mintafájlon, tartalom-alapú ellenőrzéssel lettek validálva** ebben a projektben (nem hivatalos specifikációból):
  - `0x0520` **EF_Identification** (kártyabirtokos, 143 bájt) — byte-pontosan validálva.
  - `0x0504` **EF_Driver_Activity_Data** (napi tevékenység, ciklikus puffer, byte-eltolás alapú pointer) — byte-pontosan validálva, napi bontásban vezetés/munka/rendelkezésre állás/pihenő percek + egy perc-pontos `ActivityChangeInfo` idővonal.
  - `0x0505` **EF_Vehicles_Used** (felhasznált jármű, **sorban feltöltött tömb, NEM ciklikus puffer** — a 2 bájtos fejléc a legújabb rekord 0-alapú INDEXE, nem bájt-eltolás) — byte-pontosan validálva (odométer-lánc folytonossága, valódi dátumok, tiszta rendszám-szöveg). **Gen1/Gen2 eltérő rekordméret**: gen1 31 bájt/rekord, gen2 48 bájt/rekord (egy 17 karakteres VIN-mezővel bővítve a végén) — a `walkBlocks()` ezért blokkonként eltárolja a generációt is, és `parseVehiclesUsed()` ez alapján választ rekordméretet. **Ez volt az egyetlen valódi implementációs hiba ebben a körben**: az első verzió a gen2 blokkot (ami felülírja a gen1-et, mert az utóbbi van a fájlban) gen1 rekordmérettel próbálta dekódolni, ami progresszíven elcsúszó, értelmetlen adatot (1970-es évek, azonos odométer-értékek, sérült rendszám-szöveg) produkált — csak a generációnkénti rekordméret-választás után lett tiszta az eredmény.
  - `0x0502`/`0x0503` **EF_Events_Data**/**EF_Faults_Data** (24 bájt/rekord, típus+kezdet+vég+rendszám) — a pontos FID-eket a blokk-SORREND (Application_Identification után, Driver_Activity_Data előtt) és a tiszta 24-es oszthatóság alapján azonosítottuk; **ennél a konkrét mintafájlnál mindkét blokk teljesen üres** (a sofőrnek nincs rögzített eseménye/hibája), ezért a rekord-struktúra nem validálható byte-pontosan valós, kitöltött adattal — ha egy jövőbeli feltöltésnél furcsa típus-kód/dátum jönne ki, ez a feltételezés felülvizsgálandó.
  - Ha egy blokk nem dekódolható megbízhatóan, a parser üres tömböt/`null`-t ad rá vissza + egy figyelmeztetést a `warnings` tömbben — sosem kitalált adatot.
- **`backend/interface/tachografInterface.php`**: `elemezDdd($base64, $ceg_id)` (akció: `elemezTachografDdd`) csak dekódol+javasol, nem ír DB-be; `alkalmazImport($napok, $sofor_id, $kartyaszam, $forrasFajlnev, $ceg_id, $esemenyek)` (akció: `alkalmazTachografImport`) ír ténylegesen. Sofőr-javaslat két lépcsőben: előbb `user.tachograf_kartyaszam` egyezés (pontos, egy korábbi feltöltésből), ha nincs, laza név-egyezés (ékezet-normalizált tartalmazás-vizsgálat a dekódolt vezetéknév+keresztnév és `user.name` közt) — mindkettő csak javaslat, admin bármikor felülbírálja. Jármű-egyeztetés ugyanazzal az alfanumerikus rendszám-normalizálással, mint a MOL-importnál.

- **Gotcha, amibe bele lehet futni (ismét a `build:tailwind` osztály)**: a `badgeBg` színek (`bg-sky-500`, `bg-violet-500`, `bg-pink-500`, `bg-ink-400`/`bg-ink-600`) egyike sem szerepelt korábban SEHOL a kódbázisban, ezért hiányoztak az előre lefordított `tailwind.css`-ből — élőben (Playwright screenshot + DOM-vizsgálat) a "Hangfájl" (mp3) kártya teljesen üres, szín nélküli négyzetként jelent meg, holott a DOM-ban a helyes `class="bg-sky-500"` már ott volt. `grep -c "\.bg-sky-500" tailwind.css` `0`-t adott vissza — `npm run build:tailwind` után a jelvény azonnal helyesen megjelent. **Új `badgeBg`/hasonló szín-osztály bevezetésekor mindig ellenőrizd `grep`-pel a pre-built `tailwind.css`-ben, ne csak a DOM-ban** — a helyes class-attribútum jelenléte a DOM-ban NEM garantálja, hogy a stílus ténylegesen létezik a lefordított CSS-ben.

## Fuvar-dokumentum OCR + Fuvar modul (2026-07-25)

Új, admin-only modul (**sub-project 1 of a planned 7** — Számlázz.hu-integráció, NAV kimenő-számla-követés, bank-egyeztetés fuvar-szinten, statisztikai dashboardok és a globális kereső bővítése még hátravan, ld. a teljes tervet: `docs/superpowers/specs/2026-07-25-fuvar-dokumentum-ocr-design.md`): a papíralapú fuvarlevél/szállítólevél dokumentumokból Gemini OCR-rel kinyert adatok alapján egy fuvar rögzítése 30-60 másodperc alatt legyen, a korábban (ld. "Removed: Fuvarok / Fuvartervező modulok" fentebb) tudatosan kivezetett, szóbeli/emlékezet-alapú fuvarnyilvántartás helyett — a különbség a régi modulhoz képest az, hogy az adatforrás most a fizikai dokumentum OCR-je, nem a diszpécser utólagos, gyakran elmaradó kézi rögzítése.

### Adatmodell: `beerkezett_dokumentumok` ↔ `fuvarok`

- **`beerkezett_dokumentumok`** — a feltöltött dokumentum + OCR-eredmény, mielőtt (vagy ha soha nem) fuvarrá válik: `fajl_id` → `fajlok.sorszam` (a nyers fájl), `tipus` (`fuvarlevel`/`szallitolevel`/`ismeretlen`, OCR-becsült, admin felülírhatja), `ocr_allapot` (`feldolgozatlan`/`kesz`/`hiba`), `ocr_adatok` (JSON, a kinyert mezők), `fuvar_id` (NULL, amíg nem lett belőle fuvar). Az admin inbox (`getBeerkezettDokumentumok`) alapértelmezetten csak a `fuvar_id IS NULL` sorokat listázza — ez a "feldolgozandó" nézet, nem egy `allapot` mező.
- **`fuvarok`** — a tényleges fuvar: `sofor_id`/`kamion_id`/`furgon_id` (kölcsönösen kizáró, mint a korábbi kamion/furgon-mintáknál)/`potkocsi_id`/`megbizo_id` (→ `ugyfelek.id`), útvonal (`felrako`/`lerako`/`tavolsag_km`), `fuvardij`/`egyeb_koltseg` (az "Összesen" sosincs tárolva, mindig `fuvardij + egyeb_koltseg` a lekérdezésben), `allapot` (5 érték: `rogzitett`/`szamlazasra_var`/`szamlazva`/`fizetesre_var`/`teljesitve` — **ebben a fázisban csak kézi váltással**, az automatikus váltás a Számlázz.hu/NAV-fázisokra vár). Egy `beerkezett_dokumentumok` sor és a belőle létrehozott `fuvarok` sor kapcsolata kétirányú: `beerkezett_dokumentumok.fuvar_id` mutat előre, a mögöttes `fajlok` sor pedig át van parentelve (ld. lentebb) — nincs duplikált fájltárolás.
- **`ugyfelek.fizetesi_hatarido_nap`** visszahozva (a korábbi Fuvarok-kivezetés törölte) — kizárólag ennek a modulnak a megbízó-auto-kitöltési igénye miatt, nem a régi fuvar-fizetettségi funkció feltámasztása.

### Gemini OCR-integráció (`backend/GeminiOcrClient.php`, `backend/interface/beerkezettDokumentumInterface.php`)

- **Modell: `gemini-3.5-flash`**, ingyenes kvóta-szinten, nyers curl-hívás (nem SDK — a projektnek nincs composer.json-ja). Multimodális LLM-et a kézzel írott (kurzív magyar) fuvarlevelek szemantikus kézírás-értelmezése indokolt — egy hagyományos OCR-motor ezt nem tudná megbízhatóan.
- **`maxOutputTokens: 8192` explicit beállítása kritikus**: a modell "thinking" változata a válasz-token-keretet a látható JSON ÉS a belső gondolkodási token-felhasználás közt osztja meg — enélkül a JSON-kimenet csendben, `finishReason: "STOP"` mellett (nem `MAX_TOKENS`-szel jelezve!) a közepén levágódott, amit `json_decode()` `null`-ra old fel — ez hamis "OCR sikertelen" állapotot produkált egy ténylegesen sikeres, csak túl szűkre szabott hívás után. Ez élő teszttel (Task 5) derült ki, nem kód-olvasással.
- **Kvóta/rate-limit — élőben, ismételten megfigyelt kockázat, nem csak elméleti**: a megosztott Gemini API-kulcsnak van napi ingyenes kvótája ÉS (ennél gyakrabban ténylegesen elért korlátként) egy percenkénti kérés-limitje. Ez a Task 16 golden-path-futtatása alatt is ténylegesen bekövetkezett: több egymást követő OCR-hívás rövid időn belül 2× is `ocr_allapot='hiba'`-t adott ~1 másodperces válaszidővel (szemben egy valódi, sikeres hívás ~3-13 másodperces "thinking"-latenciájával) — ez a gyors válaszidő volt a jele, hogy a hívás egy rate-limit-választ kapott, nem egy ténylegesen lefutott Gemini-elemzést. A retry (kis várakozás után) mindkétszer sikeres volt. **Ez elfogadott, jelenleg nem korlátozott kockázat** — nincs kliens-oldali throttling/backoff a `elemezBeerkezettDokumentum` actionön, és most szélesebb kör (admin ÉS sofőr sessionök is, ld. lentebb) hívhatja, mint eredetileg tervezve volt.
- **Graceful degradation hibán**: sikertelen OCR (kvóta/hálózati hiba/csonka válasz) esetén a feltöltés **mindig perzisztálódik** (`fajlok` sor + `beerkezett_dokumentumok` sor `ocr_allapot='hiba'`, `ocr_adatok=NULL`), admin kézzel tölti ki a mezőket — ez **tudatos eltérés** a Bank/MOL/Tachográf import mintájától (ott hiba esetén semmi nem perzisztálódik), mert itt kifejezett elvárás, hogy egy sofőr-feltöltés sose vesszen el egy átmeneti Gemini-hiba miatt.
- **Saját cégnév disambiguáció (`admin.cegnev`, új mező)**: az első élő teszten a modell összekeverte a dokumentum nyomtatott fejlécén szereplő saját cégünket (a fuvarozót) a tényleges megbízóval. Mivel a rendszer több tenant-ot szolgál ki, a saját cégnév nem írható fixen a promptba — a `admin.cegnev` (csak a root/tulajdonos admin sorában töltendő ki) szerver-oldalon, `ceg_id`-ből feloldva kerül bele a promptba minden híváskor, egy explicit szabállyal ("a nyomtatott fejléc cége SOSEM lehet megbízó"). Ugyanez a mező a jövőbeli Számlázz.hu-fázisban is kellhet (kibocsátó adatai a számlán).

### `letrehozFuvarDokumentumbol()` — fájl-reparenting

Fuvar dokumentumból történő létrehozásakor a mögöttes `fajlok` sor **nem másolódik**, hanem áthelyeződik: `UPDATE fajlok SET tabla='fuvar', rowid=<új fuvar id> WHERE sorszam = <fajl_id>` — ezután a dokumentum a fuvar szokásos melléklet-galériájában jelenik meg, ugyanazzal a komponenssel, mint minden más modulnál. Ez egy a kódbázisban korábban nem használt, de egyszerű minta (egyetlen UPDATE, nem új infrastruktúra). **Gotcha, amibe menet közben belefutottunk (Task 14)**: ha egy `letrehozFuvarDokumentumbol()`-lel létrehozott fuvart utólag, teszteléskor törölnek, a hozzá tartozó `fajlok` sor `tabla='fuvar'`/`rowid=<törölt fuvar id>`-n marad — **nem áll vissza automatikusan** `beerkezett_dokumentum`-ra, mert a törlés (`deleteFuvar`) csak a `fuvarok` sort soft-deleli, a `fajlok` reparentinget nem vonja vissza. Task 16 golden-path-futtatása során egy pontosan ilyen, korábbi menetből (Task 14) itt maradt dangling `fajlok` sort találtunk és takarítottunk el (`tabla='fuvar'`, `rowid`= egy már nem létező `fuvarok.id`-ra mutatva) — ha egy jövőbeli teszt-fuvart dokumentumból hoznak létre és utána törölnek, érdemes explicit ellenőrizni/visszaállítani a hozzá tartozó `fajlok` sort is, nem csak a `fuvarok` sort.

### `AutocompleteSelect` — első saját típusahasú komponens a kódbázisban

`src/components/UI/AutocompleteSelect.js` (`FuvarForm.js` Sofőr/Jármű/Pótkocsi/Megbízó mezői) az első típusahead-autocomplete komponens ebben a kódbázisban — korábban minden választó mező plain `<select>` volt. Szöveges kereséssel szűrt legördülő lista, kiválasztás után egy "chip"-szerű (kitöltött mező + "Kiválasztás törlése" gomb) állapotra vált. **Jövőbeli entitás-választó mezőknél ezt érdemes újrahasznosítani egy sima `<select>` helyett**, különösen ha a választható lista hosszú lehet (jelenleg csak a Fuvar modul él vele, de nincs oka, hogy ez maradjon az egyetlen fogyasztója).

### Schema-drift gotcha (Task 7) — `CREATE TABLE IF NOT EXISTS` csendben no-op-olt egy elavult táblán

A `fuvarok` táblának egy régebbi, teljesen más sémájú (`ugyfel_id`/`felrakas_cim`/`dij`/`statusz` oszlopokkal, egy korábbi, nem ehhez a feature-höz tartozó munkamenetből maradt) verziója már létezett a helyi dev DB-ben, amikor Task 1 `backend/sql/33.sql`-je lefutott. MySQL `CREATE TABLE IF NOT EXISTS`-a **csak a tábla létezését ellenőrzi, az oszlop-szerkezetet nem** — a migráció csendben, hiba nélkül no-op-olt, és a valódi (`sofor_id`/`kamion_id`/.../`allapot` oszlopos) séma sosem jött létre. Ez csak akkor derült ki, amikor Task 7 (`FuvarInterface`) élesben lefuttatta az első lekérdezést az elvárt oszlopok ellen, és `SQLSTATE[42S22]: Column not found` hibát kapott. Fix: `backend/sql/34.sql` (új fájl, mert `33.sql` már commitolva volt) droppolta és a helyes sémával újra létrehozta a táblát. **Általános tanulság, minden jövőbeli `CREATE TABLE IF NOT EXISTS`-alapú migrációra**: ha egy tábla névileg már létezhet egy korábbi, nem kapcsolódó munkamenetből, egy puszta "sikeresen lefutott, a tábla létezik" ellenőrzés (ahogy Task 1 saját verifikációja is tette) nem elég — a tényleges oszlop-szerkezetet (`SHOW COLUMNS`) is össze kell vetni az elvárt sémával, különben a hibát csak egy jóval későbbi, a táblát ténylegesen használó lekérdezés fedi fel.

### `fajlok.sorszam`, nem `.id` — ismét megerősítve

A `fajlok` tábla elsődleges kulcsa `sorszam`, nem `id` (ld. "Fájlok — központi fájlkezelővé bővítés" fentebb) — ez a Fuvar modulban két helyen okozott volna csendes hibát, ha nem kezelik explicit: `beerkezettDokumentumInterface::fajlnevekFeloldasa()` (`fajl_id IN (...)` ellen `SELECT sorszam, filename FROM fajlok`, nem `id`-t) és `letrehozFuvarDokumentumbol()`-nek a fenti reparenting-UPDATE-je (`WHERE sorszam = <fajl_id>`). Mindkét helyen expliciten kikommentezve, hogy jövőbeli módosításnál ne csússzon vissza `id`-ra.

### No-JOIN / no-UNION konvenció újra megerősítve

A projekt saját SQL-lintere sem `JOIN`-t, sem `UNION`-t nem enged — a Fuvar modul minden entitás-név-alapú keresése/dúsítása (`FuvarInterface::keresIdkNevAlapjan()`/`dusitSorokat()`/`batchLekerdezes()`, sofőr/kamion/furgon/pótkocsi/megbízó nevek és rendszámok feloldása egy `fuvarok` lekérdezéshez) külön `SELECT`+PHP-oldali `IN (...)`/merge mintát követ, ugyanúgy, mint a korábban dokumentált `helyszinInterface::hozzafuzMegjegyzesekSzama()`/`bejelentesekInterface::getUzenetInfok()`.

### Cross-tenant FK-tulajdonjog ellenőrzés `newFuvar`/`updateFuvar`-on

Az első implementáció (Task 7) client-submitted `sofor_id`/`kamion_id`/`furgon_id`/`potkocsi_id`/`megbizo_id` mezőket kötött be közvetlenül INSERT/UPDATE-be, ellenőrzés nélkül — ez egy cross-tenant IDOR lett volna (egy admin egy MÁSIK cég sofőrjét/járművét/ügyfelét is hozzárendelhette volna egy saját fuvarhoz, ha kitalálja/megsejti az id-t). Fix (még Task 7 alatt, review-találatból): minden nem-üres FK id-t `ervenyesEntitasE($tabla, $id, $ceg_id)` ellenőriz írás előtt (`WHERE id = :id AND admin = :ceg_id AND torolt <> 'I'`), plusz olvasáskor is (`egyMezoLekerdezese()`/`batchLekerdezes()`) `AND admin = :ceg_id` védelem — ugyanaz a kétrétegű (write-time + read-time) minta, mint a 2026-07-19-i biztonsági audit óta a többi modulnál.

### `MODULE_PERMISSION_MAP` tudatos kompromisszum — `elemezBeerkezettDokumentum` admin-szerepkör-ellenőrzés nélkül

`elemezBeerkezettDokumentum`-ot eredetileg (Task 5) a `MODULE_PERMISSION_MAP`-ban `['fuvarok', 'szerkesztes']`-ként regisztrálták, admin-only feltételezéssel. Amikor a sofőr-oldali fuvarlevél-feltöltő (Task 15) implementációja alá ért, kiderült: ez az action mindkét munkamenet-típusból (admin ÉS sofőr) hívandó, de `requirePermission()` saját maga is `resolveKerelmezo()`-t hív a `validation()` lépésben, MIELŐTT a case-ág egyáltalán lefutna — tehát a case-ágban való `resolveSajatCegId()`-re váltás önmagában nem lett volna elég, a `MODULE_PERMISSION_MAP`-bejegyzés a sofőr-hívást már a validáció szintjén elvéreztette volna. **A fix a `MODULE_PERMISSION_MAP`-bejegyzés teljes eltávolítása volt** (nem csak egy admin/sofőr-ág hozzáadása hozzá), pontosan ugyanaz a minta, mint a többi, mindkét szerepkörből hívható action (`fileUpload`, `getHelyszinek`, `globalSearch`) esetén, amik szintén hiányoznak ebből a map-ből.

**Explicit, szándékosan dokumentált mellékhatás (a review kifejezetten kérte, hogy ez itt, nem csak a review-jegyzőkönyvben szerepeljen)**: ez azt is jelenti, hogy a per-szerepkör, admin-configurálható `fuvarok`/`szerkesztes` jogosultság (a `Jogosultságok` oldalon) **ettől az EGY konkrét actiontől kezdve nem érvényesül** admin/csapattag hívóknál sem — bármely hitelesített admin-csapattag ki tudja váltani az OCR-elemzést + inbox-beszúrást, függetlenül a saját, konfigurált Fuvarok-modul jogosultságától. A `letrehozFuvarDokumentumbol`, `getBeerkezettDokumentumok` és `updateBeerkezettDokumentumTipus` viszont **továbbra is helyesen jogosultság-ellenőrzött** marad. Ez egy tudatos, alacsony súlyosságú kompromisszum — az action legfeljebb egy review-only inbox-bejegyzést hoz létre, sosem egy valódi `fuvarok` üzleti rekordot —, de expliciten dokumentálva van, hogy egy jövőbeli `MODULE_PERMISSION_MAP`-diffelő ne kelljen újra levezetnie az indoklást.

### Golden-path végigfuttatás (Task 16) — élőben tesztelve, mindkét szerepkörrel

Playwright-tal, a helyi `sessions` táblába illesztett valódi admin- és sofőr-munkamenettel: sofőr feltöltötte a fuvarlevél mintát (`/user/dokumentum-feltoltes`) → admin látta az OCR'd dokumentumot a `/admin/beerkezettDokumentumok` inboxban → admin feltöltötte a szállítólevél mintát is közvetlenül az inboxból → "Fuvar létrehozása" a sofőr-feltöltésből, az OCR többplacás rendszám-bizonytalanságát (`"RLP-018, WCS-314"`, a tervben is dokumentált jelenség) kézzel javítva a helyes egyetlen jármű kiválasztásával → `/admin/fuvarok` lista, keresés felrakó szerint, rendezés "Teljesítés" szerint mindkét irányban, `allapot` váltása `rogzitett` → `szamlazasra_var` → `teljesitve` végig, egy külön teszt-fuvar létrehozása+törlése (eltűnik a listából) → mindhárom új oldal (`BeerkezettDokumentumok.js`/`Fuvarok.js`/`FuvarForm.js`, utóbbi az autocomplete legördülő nyitott állapotában is) sötét módban ellenőrizve, fehér/stílus nélküli terület nélkül. Az egyetlen, a futtatás során ténylegesen tapasztalt hiba a fent dokumentált Gemini rate-limit volt (nem kód-hiba, retry-jal megoldva). A golden-path-futtatás által létrehozott egy fuvar (Dunakeszi → Páty, `id=19`) és a hozzá tartozó OCR-forrásdokumentum (`beerkezett_dokumentumok.id=22`) szándékosan **megmaradt** demo-rekordként; minden egyéb, a Task 1-16 verifikációi során felhalmozódott teszt-`beerkezett_dokumentumok`/`fajlok`/`fuvarok`/`sessions` sor törölve lett.

Minden tétel "Megnyitás" gombja a Táblázat nézetre vált és a keresőt a fuvar **`felrako`** mezőjére (nem a megjelenített "A → B" útvonal-stringre!) tölti elő — **valós hiba, amit élő teszt fogott meg**: a backend keresése soronként, egy-egy oszlopra fut LIKE-kal (`felrako LIKE :search OR lerako LIKE ... OR ...`), ezért a kombinált "A → B" string egyik oszloppal sem egyezik, 0 találatot adott, amíg a `felrako`-only preset-re nem lett javítva. Ugyanaz a `key`+`initialSearch` remount-minta, mint a Pénzforgalom "Tétel↔Jármű" kereszthivatkozásánál.

Minden fenti backend-módosítás `php8.2 -l`-lel lint-ellenőrizve, minden frontend-módosítás valós, helyi `sessions`-be szúrt admin-munkamenettel, Playwright-tal élőben leellenőrizve (ideiglenes teszt-fuvarokkal/megbízó-határidővel, utána törölve/visszaállítva) — beleértve a fenti `felrako`-vs-`utvonal` keresési hibát is, amit csak élő kattintás-teszt fedett fel, nem a kód átolvasása.

## NAV számla teljesítés/fizetési határidő, és Pénzforgalom dátum-alap váltó (2026-07-26)

Két, egymásra épülő kiegészítés a NAV Online Számla importhoz és a Pénzforgalom oldalhoz, felhasználói kérésre.

- **`egyeb_koltsegek` két új oszlopa** (`backend/sql/40.sql`): `teljesites_datum`/`fizetesi_hatarido` DATE NULL. A NAV digest (`InvoiceDigestType`) ezt a két mezőt (`invoiceDeliveryDate`/`paymentDate`) már korábban is szolgáltatta — előbb csak a NAV import review-táblázatában jelentek meg (ld. a `NavSzamlaClient::digestSorFeldolgozas` kommentje), most `NavSzamlaInterface::importalSzamlak()` is menti őket. A mezők a "Új tétel"/szerkesztés formon kézzel is kitölthetők (opcionális), és megjelennek a Tételek lista két új, rendezhető oszlopaként — a fizetési határidőnél a jármű-adatlapok lejárati mezőinél már bevált `LejaratTag` komponens (piros=lejárt, borostyán=≤7 nap) adja a sürgősségi jelzést, most először egy nem-jármű kontextusban újrahasznosítva.
- **Pénzforgalom "Dátum alapja" szelektor** (`PeriodControl` a fejlécben, `Koltsegek.js` `datumAlap` state, alapértelmezetten `"datum"`) — a Dátumtól/Dátumig mostantól három alap közül választhatóan szűr: kiadás/felvétel dátuma (`datum`, változatlan alapértelmezés), teljesítés dátuma, fizetési határidő. **Csak azokra a mennyiségekre hat, amiknek ténylegesen van teljesítés/fizetési-határidő fogalmuk** — vagyis kizárólag a kézzel rögzített/importált `egyeb_koltsegek` sorokra (Tételek lista, KPI-sor, kategória-rács, Jármű szerinti bontás, Havi alakulás, KPI %-delta előző-időszak számítás). A karbantartás-táblák, a `tankolasok`, az on-the-fly számolt biztosítás/bér **mindig a saját `datum` oszlopuk szerint szűrődnek**, függetlenül a választott alaptól — nincs más dátumuk, amit használhatnának, és ez szándékos, nem hiányosság (a szelektor mellett egy tooltip magyarázza el). Backend oldalon `koltsegInterface.php`'s `egyebHavonta()`/`egyebJarmuvenkent()`/`egyebNemKotott()` privát helperei (és rajtuk keresztül `getKoltsegOsszesito()`/`getOsszesenGyors()`/`getEgyebKoltsegek()`) kaptak egy fehérlistás `$datumMezo` paramétert (`normalizDatumMezo()`, `DATUM_MEZOK` konstans) — a `havonta()`/`jarmuvenkent()`/nyers `tankolasok`-lekérdezések/`getBiztositasKiadasok()`/`getBerKiadasok()` hívások **szándékosan nem** kapják meg (azok a nem-váltható forrásokat számolják). A Fuvarok "Statisztikák" fülének fuvarozási profit-riportja (`getUzemanyagKiadasHavonta`/`getBerKiadasHavonta`/`getUtdijKiadasHavonta`) is kimarad ebből — az egy másik, önálló funkció, változatlanul `'datum'` alapon marad.
- **Gotcha, élő teszttel felfedezve, nem a kód átolvasásával**: `Koltsegek.js`'s `handleUjTetelChange` (az "Új tétel" form összes mezőjének közös `onChange`-e) feltétel nélkül hívta `e.target.setCustomValidity("")`-t minden változáskor — ez rendben van egy valódi `<input>`-nál, de a `DatePicker.js` `onChange`-e egy szintetikus `{ target: { name, id, value } }` objektumot ad át (nem valódi DOM-eseményt), aminek nincs `setCustomValidity` metódusa. Emiatt **a form MINDEN dátummezője** (a most hozzáadott kettő ÉS a már régóta létező "Dátum" mező is) TypeError-ral elhasalt minden kattintásnál, mielőtt a `setUjTetel()` state-frissítés lefutott volna — a dátum a gyakorlatban sosem volt módosítható a naptár-nézeten keresztül. Ez egy már korábban is létező, észrevétlen hiba volt, nem ebben a körben okozott regresszió — csak azért derült ki, mert ez a menet élőben, Playwright-tal, ténylegesen rákattintott a dátumválasztóra (a korábbi menetek dokumentáltan csak a szöveges mezőket, kategória-váltókat stb. teszteltek ezen a formon). Fix: `e.target.setCustomValidity?.("")` (opcionális láncolás) — a `handleUjTetelInvalid`-nál (a szöveges/szám mezők natív `onInvalid`-ja) ez nem probléma, mert ott mindig valódi DOM-target van.
- **Élőben tesztelve** (nem csak kód-olvasással): valós, helyi `sessions`-be szúrt admin-munkamenettel, Playwright-tal — egy teszt-tétel mindkét új dátummezővel felvéve és DB-ből visszaellenőrizve, szerkesztés-előtöltés megerősítve, egy valós NAV-tétel importálva és DB-ből megerősítve, hogy a teljesítés/fizetési határidő ténylegesen bekerült (nem csak a review-táblázatban látszik), és a "Dátum alapja" váltása mindhárom opción ténylegesen megváltoztatta a Tételek lista tartalmát ÉS a KPI-sor számait a várt irányba (egy `fizetesi_hatarido`-n kívül eső tétel eltűnt a listából, a Bevétel KPI 0 Ft-ra esett, mert a bevétel-sorok túlnyomó többségének nincs fizetési határideje). A teszt-adatok (tétel, importált NAV-sor, munkamenet) utána törölve lettek.

## Fuvar OCR-bővítés: távolság (km) + tömeg (kg) (2026-07-26)

A `GeminiOcrClient::buildPrompt()` JSON-sémája két numerikus mezővel bővült:
`tavolsag_km` és `tomeg_kg` (a fuvarlevél/szállítólevél alján gyakran
szereplő adatok) — a modell explicit utasítást kap, hogy mértékegység
nélküli, tiszta számot adjon vissza, és tonnában megadott tömeget kg-ra
váltson (1 t = 1000 kg). `fuvarok` kapott egy `tomeg_kg DECIMAL(8,2) NULL`
oszlopot (`backend/sql/41.sql`, `tavolsag_km` mellé) — a távolság oszlop már
korábban is létezett kézi mezőként, csak az OCR nem töltötte ki soha.
`FuvarInterface::letrehozDokumentumbol()` mostantól mindkét mezőt átveszi az
`ocr_adatok`-ból az új fuvar létrehozásakor; `FuvarForm.js` "Útvonal"
szekciója kapott egy "Tömeg (kg)" mezőt a "Távolság (km)" mellé, és mindkettő
előtöltődik az OCR-előnézetből (`ocrAdatokToForm()`). A `suly` OCR-mező
(korábban a sémában szerepelt, de sosem volt hozzá tábla-oszlop/mapping)
ezzel a menettel lett ténylegesen kiváltva a `tomeg_kg`-vel — maga a `suly`
mező a sémában maradt, de továbbra sincs hozzá felhasználás, nem lett
eltávolítva (alacsony kockázatú holt mező, nem ez volt a kör tárgya).
Élőben tesztelve: `FuvarInterface::letrehozDokumentumbol()` közvetlen PHP
CLI-hívással (kézzel beszúrt `ocr_adatok` JSON-nal, valódi Gemini-hívás
nélkül, a kvóta-kockázat elkerülésére), majd a teljes UI-útvonalon
Playwright-tal (`/admin/fuvarForm` → mentés → `fuvarok` tábla ellenőrzése) —
mindkét mező helyesen mentődött, a teszt-sor/session utána törölve.
